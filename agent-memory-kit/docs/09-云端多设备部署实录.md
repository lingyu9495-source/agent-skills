# 09 · 云端一座：多设备、多智能体共用的部署实录

> 本文是实机勘查结论，不是设计设想。样本：一台 2 核 4G 云服务器，18 个成员账号，3998 条记忆，连续运行 1 周 3 天，实占内存 104MB。

---

## 一、什么时候要从"单机"升到"云端一座"

| 信号 | 说明 |
|---|---|
| 你有两台以上常用设备 | 家里电脑、公司电脑、云机各记一套，等于三份残废记忆 |
| 团队有三个人以上在用 AI | 各存本地，谁也看不到谁的沉淀 |
| 用的框架不止一个 | Hermes / WorkBuddy / 豆包 / Claude Code 各记各的 |
| 手机也要用 | 手机端跑不了完整数据库，只能连服务 |

单机版解决"一台机器"，云端版解决"一座服务，全员当客户端"。

---

## 二、架构长什么样

```
    家里电脑 ─┐
    公司电脑 ─┤  ovmem / HTTP 桥          ┌─ 私有库 A
    云  机  ─┼─────────────────────────▶│─ 私有库 B
    手  机  ─┘     api_key 认证           └─ 私有库 C
                     │
              记忆底座服务（常驻）
              embedding 语义索引
              一人一库 · 硬隔离
                     │
              共享事实层（知识总桶）
```

三条规矩：

1. **服务只有一个，客户端可以有很多**。客户端就是薄薄一层 HTTP 调用，不需要在每台机装数据库
2. **一人一库，硬隔离**。成员之间默认互相看不到（实测：A 账号搜 B 的内容 0 命中）
3. **共享走事实层，不走共用大池**。团队共识、口径、方法论放知识层；私人记忆各归各

> 别踩这个坑：想靠"建个 group 把大家拉进去共享记忆"——实测无效，加组后搜别人库仍是 0 命中。要共享就做事实层。

## 三、部署步骤

### 1. 服务端

```bash
# 独立 venv，不污染系统 python
python3 -m venv /opt/memory/venv
/opt/memory/venv/bin/pip install -r reqs.txt

# systemd 常驻 + 内存限额（4G 机器给 1GB 足够）
# /etc/systemd/system/memory-base.service
[Service]
ExecStart=/opt/memory/venv/bin/server
Restart=always
MemoryHigh=700M
MemoryMax=1100M

systemctl enable --now memory-base
```

### 2. 模型配置

- 向量：`text-embedding-v4`（1024 维）——决定召回质量，不要省
- 视觉：`qwen3-vl-plus`——截图/照片进记忆要用
- 限流（**关键**）：`batch_size=8`、`max_concurrent=1`、`max_retries=6`
  - 不设这个，embedding 429 会**静默丢记忆**，表现为"接了但什么都没记住"

### 3. 建账号

一个成员一个 user + 一个 key，key 文件权限 600，**不进日志、不进代码库**。

```bash
POST /api/v1/admin/accounts/<account>/users   {"user_id":"<成员>","role":"user"}
# 返回 user_key —— 只给该成员本人，落盘 chmod 600
```

> 坑：已有的成员不能重复 POST（返回 409）。取回 key 用 `GET /api/v1/admin/accounts/<account>/users` 列表里的 `api_key` 字段，别重新建号。

### 4. 客户端接入（按实际框架选一个）

| 框架 | 接法 |
|---|---|
| 任意语言/框架 | 直接调 HTTP：`POST /api/v1/memory/write`、`POST /api/v1/search/find` |
| 命令行/脚本 | `ovmem remember / search / ask / health`（7KB Python 单文件） |
| Hermes | 内置 provider 直连 |
| 其他（QwenPaw / DSH / OpenClaw） | 按各自会话格式写 100–150 行薄桥，挂定时器增量抽取 |

配置就三行（`~/.ovmem.conf`）：

```
OVMEM_URL=http://127.0.0.1:1933    # 或隧道/反代后的地址
OVMEM_USER=你的账号
OVMEM_KEY=你的key
```

### 5. 网络

- 不要裸奔公网 HTTP。要么安全组按 IP 白名单放行，要么走 SSH 隧道：

```bash
ssh -f -N -L 1933:127.0.0.1:1933 user@server
```

- 团队多人使用时，前面加反代 + HTTPS

## 四、验收（三步，缺一步不算成）

1. `ovmem health` 返回 `healthy: true`
2. 写一条 → 搜得到（`remember` 后 `search` 命中，且 score 有明显区分度）
3. **换一台设备**，用同一个 key 搜同一条 → 也命中

第三步才是"多设备共用"的证据。前两步只能证明服务活着。

## 五、运维清单

| 项 | 做法 |
|---|---|
| 备份 | 每日打包 data 目录，保留 7 天，异地存一份 |
| 巡检 | 看 `server.log` 里的 `429`、`TimeoutError`、`Conflicting` |
| 扩容 | 成员数上去先看向量库体积与内存占用，2C4G 可撑 20 人量级 |
| 迁移 | 明文 + 向量库整目录拷走即可，不锁死厂商 |

## 六、三个已知故障（真实出现过）

1. **写入静默丢失**：embedding 限流 429 时不报错，条目没进库。判据：写完后立刻搜，搜不到就是丢了
2. **意图分析超时**：请求里带 intent 抽取的，超时后降级为原始 query，检索质量下降但不报错
3. **并发写冲突**：同一条目被两个进程同时改，报 `Conflicting add/update/delete results for URIs`。做法：写入串行化，加 flock

## 七、成本口径

| 项 | 数量级 |
|---|---|
| 服务器 | 1 台 2C4G（现有机器即可） |
| 内存占用 | 约 100–200MB（20 人以内） |
| 向量库 | 4000 条记忆约 30MB |
| embedding 调用 | 每条记忆一次，随写入量线性 |
| 对比大厂记忆服务 | 按量计费 vs 固定服务器成本 |
