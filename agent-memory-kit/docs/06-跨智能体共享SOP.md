# 跨智能体共享记忆 SOP（一底座 · 多智能体）

> 单个 AI 有长期记忆，这件事不值钱。值钱的是：**同一台机器上的所有智能体，共用一份记忆。**
> 你今天用豆包、明天 WorkBuddy、后天 Hermes、再换 Claude Code / 扣子 / 龙虾 —— 换的是工具，不是记忆。

---

## 一、架构（只有三种节点，别想复杂）

```
             ┌─────────────────────────────┐
             │   共享记忆底座（唯一主库）    │  ~/.ai-memory
             │  MEMORY.md  facts/  archive/ │
             │  index.db（FTS5 全文索引）    │
             └───────────┬─────────────────┘
                         │ 读写同一目录
   ┌─────────┬───────────┼───────────┬─────────────┐
 Hermes    WorkBuddy    豆包      Claude Code      扣子/其他
 (AGENT=  (AGENT=     (AGENT=    (AGENT=          (AGENT=
  hermes)  workbuddy)  doubao)    claude-code)     coze)
```

- **主库唯一**：一台机器只允许一个可写主库。两个主库 = 两份互相不知道的记忆 = 假共享。
- **成员只读镜像**（可选）：多台机器时，成员机保留一份只读副本用于离线召回，定期从主库同步。
- **不放在同步盘里**：OneDrive/坚果云同步 SQLite 会在锁文件上打架，主库放本地路径，用 `digest` 产出的 Markdown 做跨机同步。

---

## 二、三步接入（每个智能体都走这三步）

### 第 1 步：指向同一个目录

```bash
export AI_MEM_DIR=~/.ai-memory      # Windows: C:/Users/你的名字/.ai-memory
```

写进 shell 配置（`.bashrc` / `.zshrc` / Windows 用户环境变量），别只在一个终端里 export。

### 第 2 步：给这个智能体一个名字

```bash
export AI_MEM_AGENT=doubao          # 或 workbuddy / hermes / claude-code / coze
```

这个名字决定它写进去的记忆打谁的标签。**不设就会全部落到 `cli`，团队视图直接失效**（最高频的错）。

临时用也可以：`ai_mem add "..." --as workbuddy`。

### 第 3 步：接两个钩子（开工读、收尾写）

| 时机 | 动作 | 具体 |
|---|---|---|
| 会话开始 | `ai_mem inject --days 7` | 输出追加到系统提示 / 首条 user 消息 |
| 会话结束或阶段完成 | `ai_mem add "结论" --kind knowledge` | 只写**确认过的结论**，不写推测 |

---

## 三、各工具的具体接法

| 工具 | 钩子放哪 | 备注 |
|---|---|---|
| **Hermes** | `AGENTS.md` 或 profile 的 `SOUL.md` 里写死两句：开工 inject、收尾 add | 最自然，天然支持本地命令 |
| **Claude Code** | 项目根 `CLAUDE.md` 加一段；或用 `memory_hook.py` 包一层 | 见 `examples/claude-code/` |
| **WorkBuddy / 豆包** | 自定义指令 / 人设里写："每次对话先读取 `ai_mem inject` 的结果" | 不能自动跑命令的，就让它**手动贴**一次 inject 输出到对话开头 |
| **扣子 / 工作流平台** | 工作流第一步调 CLI（HTTP 节点或代码节点执行本地命令） | 平台无本地执行时，退化为"人贴" |
| **任何能跑命令的智能体** | 同上两步 | 接口只有 inject 和 add，不需要 SDK |

> 关键认知：**共享底座不要求各工具"接入生态"，只要求它能读一段文本、能写一条命令。** 所以豆包这种封闭产品也能参与共享 —— 人手动贴一次注入块即可。

## 四、写入规约（不写规约，三个月后库就废了）

| kind | 写什么 | 不写什么 |
|---|---|---|
| `fact` | 已发生、可核对的事（日期、金额、决定） | 猜测、如果、大概 |
| `pref` | 人的偏好与硬规矩 | 一次性的临时要求 |
| `event` | 有待办属性的事（时间点、deadline） | 已完成的事（那是 fact） |
| `knowledge` | 结论、方法、踩过的坑、验证过的阈值 | 未复现的经验 |

四条硬规矩：

1. **一事后一条**，不要把三件事塞进一句。
2. **带上主语和数字**："客户压价 5%" 而不是 "客户嫌贵"。
3. **推断不进库**：AI 自己总结的"用户可能喜欢 X"写进去，三轮之后就成了"铁律"。
4. **重复就合并**：同一个 rid 内容重复写，先 `recall` 查一遍再 add。

## 五、团队共享（多智能体 = 团队）

### 场景 A：一台机器上多个工具（最常见）

一个主库，多个 `AI_MEM_AGENT`。`ai_mem sources` 就是团队看板。

### 场景 B：多个成员各有自己负责的智能体

两种切法，选一种：

| 切法 | 结构 | 适用 |
|---|---|---|
| 一团队一库 | 一个主库，所有人共写，`--as 人-工具` 区分 | 小团队、互信、要"共同记忆" |
| 一人一库 + 团队库 | 每人一个私有底座，团队库只沉淀共享知识点 | 有客户隔离要求 |

一人一库时，团队库的写法是"人工摘取知识点"——`knowledge` 类跨人共享，`fact` 留私有。

### 场景 C：多客户交付

**一客户一目录**（`AI_MEM_DIR=~/clients/客户A/.ai-memory`）。客户之间绝不共用底座，这是硬线。

## 六、日常巡检（每周 2 分钟）

```bash
ai_mem sources          # 谁在用、各记多少、最后一条是什么；某个智能体长期 0 条 = 没接上
ai_mem stats            # 总条数、智能体数、体积
ai_mem digest --month 2026-11   # 月度归档，沉淀成 Markdown 给团队看
```

- 某智能体长期没有新记忆 → 钩子断了（最常见是换了目录或忘了 export）
- 条目暴涨但 `knowledge` 不动 → 只在记流水，没在沉淀
- `MEMORY.md` 超 8KB → 该修剪，细节沉归档（见 `08-技能-记忆修剪与归档.md`）

## 七、七种失败模式（都是真实踩过的）

1. **假共享**：三个工具设了三个 `AI_MEM_DIR`，看着在用一个底座，其实各写各的。
2. **来源不标**：全叫 `cli`，出问题没人认领。
3. **只写不读**：`add` 天天跑，`inject` 一次没接，记忆等于锁抽屉。
4. **热层当仓库**：`MEMORY.md` 涨到 50KB，注入被截断，重要规矩反而丢了。
5. **把推断当事实**：见上。
6. **知识不沉淀**：只记流水，用一年也不聪明。
7. **同步盘放 SQLite**：多机同步后索引损坏，只能重建（数据没丢，索引要重扫）。

## 八、验收（共享场景专用）

1. 在 A（豆包）说一句暗号 → `ai_mem add "暗号：蓝鲸" --as doubao`
2. 换 B（Hermes）→ `ai_mem recall 蓝鲸` 必须命中，且显示 `@doubao`
3. `ai_mem sources` 里两个智能体都在，条数对得上
4. 把 `AI_MEM_DIR` 指到别的空目录，同一个词必须搜不到（证明不是缓存）

四步全过，才叫"共享"接上了。
