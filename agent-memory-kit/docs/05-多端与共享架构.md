# 05 · 多端与共享架构

## 一个团队只允许一个主库

两个主库并行 = 记忆分裂。三个月后没人知道哪条是真的，也修不回来。

## 三层地理：主库 / 兜底 / 镜像

```
        ┌──────────── 主库（唯一可写）────────────┐
        │  常驻云机 · 一成员一账号 · 每天备份      │
        └───────────────┬─────────────────────────┘
                        │ 单向同步（只读镜像）
        ┌───────────────┴───────────────┐
   ┌────┴─────┐                   ┌─────┴──────┐
   │ 本地兜底  │ ← 断网时写这里      │ 只读镜像    │ ← 人看得懂、能带走
   │ (笔记本)  │   恢复后回流        │ (Obsidian) │
   └──────────┘                   └────────────┘
```

规则：
- **主库唯一可写**，镜像只读
- 断网时写本地，恢复后**按时间戳回流**，冲突以主库为准
- 镜像不做全量反推，避免把草稿污染主库

## 团队共享 ≠ 共享记忆内容

实测结论（2026-11）：

- 给所有人建一个组、加进同一个 group：**只解决权限分组，不共享记忆内容**。一人一库是硬隔离。
- 想让"所有人看到团队口径与成果"，正解是**另一个东西**：一个共享的成果库（知识总桶），
  底座继续一成员一库，各管各的私记忆。

一句话：**共享的事实走成果库，私人的记忆各管各的。**

## 多机接同一个底座

客户端只需一个薄壳（100-150 行），不绑框架：

```bash
# 通用客户端形态
export MEM_URL=https://your-memory-host
export MEM_USER=<成员 slug>
export MEM_KEY=<每人一把>
mem search "关键词"     # 查
mem add "结论"          # 写
mem health              # 探活
```

要点：
1. 一成员一账号，**key 不共用**
2. 配置优先级显式写死：环境变量 > 用户级 > 系统级（否则会静默写到别人的库）
3. 每天备份 data 目录，保留 7 天
4. 端口按 IP 白名单放行；公网必须 api_key + 反代 + 限流

## 灾备

- **备份**：每日打包 data 目录（tar），保留 7 天；有条件的再加一份异地
- **恢复演练**：每季度真恢复一次到临时目录，跑一遍验收四步
- **不做**：只备份不演练（等于没备份）、把备份和主库放同一块盘

## 迁移（换机/换框架）

灵魂（记忆）与身体（运行时）分开搬：

1. 先停写，导出 `facts/`、`archive/`、`MEMORY.md`、`index.db`
2. 新机装同版本底座 → 放回同一 `AI_MEM_DIR` → 重建索引
3. 跑验收四步（重点是第 3 步跨会话召回）
4. 确认新机通了，再切流、再清旧机

**绝不**新机旧机同时写同一个库。
