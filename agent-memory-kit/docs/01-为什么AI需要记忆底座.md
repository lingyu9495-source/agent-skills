# 01 · 为什么 AI 需要记忆底座

## 一句话

**它不是忘了，是想不起来。**

所有 Agent 框架都能"存"——对话全量落库，磁盘在就一直在。
但每一次喂给模型的只有最近一段对话，更早的内容躺在库里，**没人去翻**。
于是一个用了三个月的助手，对你的了解还不如第一天看的那份简介。

## 三层时间尺度（判断"失忆"到底发生在哪层）

| 层 | 跨度 | 谁决定 |
|---|---|---|
| **存储** | 永久 | 磁盘在就一直在 |
| **上下文** | 几轮到几万字 | 模型窗口 |
| **实际记得** | 几天到两三周 | **有没有人把它捞回来** |

所谓"AI 失忆"，99% 是第三层断的：东西还在，但没进上下文。

## 框架自带记忆够不够

| 框架 | 记忆落在哪 | 上限 | 超了怎么办 |
|---|---|---|---|
| Hermes | `MEMORY.md` / `USER.md` + 会话库 | 热层硬顶（默认 22,000 字符） | 自动压摘要；旧会话需主动搜 |
| QwenPaw | sqlite `conversation_history` | 全量存 | 只拼最近若干轮进上下文 |
| OpenClaw | `sessions/*.jsonl` + 笔记目录 | 全量存 | 同上 |
| DSH | `session.v4.jsonl.zstd` | 全量存 | 同上 |
| Claude Code | `CLAUDE.md` + 会话 | 文件大小 | 靠人写，不自动 |

结论：**单人轻量使用，框架自带够用**。一旦是多人团队、或要交付给客户，靠"每个 AI 都自觉写记忆"不成立——
它饿了不会自己去找吃的，你得给它一个"开饭"的动作。

## 记忆底座必须做四件事

缺一件就退化：

1. **写入**——什么值得记（抽事实，不是存原文流水）
2. **存储**——明文、可读、可备份、可迁移
3. **召回**——按语义/关键词/时间，把相关几条塞回上下文
4. **治理**——去重、过期、遗忘、成员隔离

多数开源项目在第 1、3 件上很强，在第 4 件上很弱。
实际用起来翻车的，几乎全在第 4 件。

## 别把这三样混成一件事

| 东西 | 是什么 | 能不能当记忆底座 |
|---|---|---|
| 知识库 / Obsidian / 双链图谱 | 人写给**人**看的笔记，图谱是笔记之间的引用关系 | ❌ 没有自动抽取与按需召回 |
| RAG 检索库 | 文档切块、转向量、按问题捞片段 | 🔶 半个。能查资料，不会记住你说过什么 |
| 记忆底座 | 谁、何时、说过/决定过什么；自动写入、自动召回、可遗忘 | ✅ |

**判据**：只能靠 AI 主动去搜的，是**书库**；能自动记、需要时自动想起的，才叫**记忆**。

Obsidian 的正确用法是**外脑 + 镜像**：底座管记忆，Obsidian 管人看得懂、审得动、带得走。
两者叠加，不是二选一。

## 什么时候该装

装：
- 多人共用一套助手，需要"谁说过什么"不串味
- 交付给客户，客户期望"它记得我们"
- 项目周期长，跨月的事实、口径、决定需要可追溯
- 同一个助手要跨会话连续工作

不装：
- 单人、短任务、一问一答
- 只是想让 AI 读一批文档（那是 RAG，不是记忆）
