# 投行级重大项目可行性研究报告 · 生产方法论

## 触发条件
- 「写一份XX的可行性研究报告」且体量大（几万~几十万字）或要求「投行级/专业/Word」
- 点名「30万字」「25万字」「做成Word文档」「要专业」
- 客户/用户要一份给发改委、银行、董事会、政府招商用的正式可研
- 项目是**大型产业集群/多板块/多期**（单一项目写几十万字=注水，会一眼被看穿）

## 核心原则（用户偏好，必须内嵌）
1. **先研究方法论、确认后再写正文**——用户多次纠正「先研究怎么写，等我确认了再写」。收到需求先立方法论/施工蓝图让用户过目，确认动笔姿势再铺开正文，不要一上来就写正文。
2. **全简体中文、零英文**——客户看不懂英文。财务术语、缩写、公式变量一律中文表述（`财务内部收益率`而非`IRR`、`财务净现值`而非`FNPV`、`偿债备付率`而非`DSCR`、`息税折旧摊销前利润`而非`EBITDA`）。正文/表格/公式不出现英文词。
3. **缺数据留空、贴合现有材料、不注水**——没有的核心数据标「待尽调/待测算」，用用户已给的数据框架；绝不编造。深度靠项目本体的价值挖掘，不靠市场数据堆砌。
4. **客户角度**——回答客户最关心三问：①项目能不能做 ②应该怎么做 ③有没有市场机会。开篇结论先行。
5. **防注水铁律**（写每部分前自检）：①先写资本测算再写文字（数字先行）②护城河具体到数字（船台多少万吨/岸线多长/哪个船级社资质/冷库吨位）③价值创造逻辑独立成立（离开集团能否独立活）④协同必须「对外第三方买单」（不是左手倒右手，会被审贷官认定内部倒手）⑤市场数据标注来源+年份。
6. **分册=报告的章节，不是独立文件**——用户曾问「这些九大分册是什么东西？跟报告有关吗？」。因为他这项目本身就是产业集群，报告正文自然按板块分章展开。**向用户说明结构时，一定要讲清「分册就是这份可研报告的正文章节（因为项目是九大产业集团，报告就分九章写详实），最后合成一份Word，不是九份」**，提前打消「是不是另起炉灶/会不会是九份报告」的疑虑。
7. **项目公司=拟设立，站客户角度研判**——客户给的多是「未来要成立的项目公司」（如"百世和"），不是已存在实体。报告是**站在客户角度帮他研判「这个项目能不能做/怎么做/有没有机会」**，不是给已存在公司做后续报告。①明确区分「已有控股主体」vs「拟设立项目实施主体」，别把拟设主体吹成已有多年经验（审贷官/评审一眼看穿自相矛盾）；②除非客户点名，**不做企业尽调/不管那些公司**，只管项目可行性本身；③海森特等既有基地只作「区位/载体」提及。
8. **交付前多模型真实审核（强制）**——用户明确要求用真实聪明模型（Kimi/豆包/千问/智谱）严格通读审核，**绝不用主模型pro冒充**。delegation是全局单模型配置，派不同模型审核要先 `hermes config set delegation.model/provider <model> --profile default` 切到对应模型再派单，每个模型派完后轮换。派单前先测各模型key可用性，失效的补一个可用免费聪明模型（实测：豆包正确id=doubao-seed-2-1-turbo-260628、智谱glm-5.2免费可用可替代千问/豆包，Kimi 401、千问免费额度耗尽需充值）。**审核任务必须写「通读全部全文（14个文件），不许只抽查」**——否则子代理会偷懒只读前几个分册。⚠️ 20万字级全文审核**优先用「目标模型直连 API 送全文」而非 delegation 子代理**（子代理继承pro、且把22万字塞子代理会撑爆上下文；直连API两模型并行、各自落盘更稳）——工程实现（Kimi reasoning_content 兜底 / >300s 用 background / 别加`&`双重后台 / reportlab 不支持 span）见 `references/multi-model-review-and-qa.md`「二·补2」。

9. **修订交付物必须「客户干净版」，绝不把内部评审/否定意见打进交付物**（用户 2026-09-07 纠正，重要）——审核发现的问题用来指导修改，但交付给客户的是**一份改干净的修订报告本身**，不是「评审意见＋修改说明＋待补数据清单」这种暴露内部评审过程的文档。用户原话：「改好后是给客户看的，客户要看你怎么修订怎么否定的吗？」。①评审/否定/问题清单是**内部工作底稿**，存知识库供自己复盘，**绝不作为交付物发给客户**；②发给客户的是修订后的成品报告，把评审时误写的表述、打架的口径、误导的定性**在成品里直接改掉**，客户看不到「我们原来哪里写错了」。

**9a. 客户版标题/文件名不标版本状态字样**（用户 2026-09-07 二次纠正）——除删掉内部评审痕迹外，客户版的文件名、封面、标题**也不带「初稿/报批稿/待尽调核实版/送审稿/草稿/V2」这类版本状态标签**。用户原话：「不要写什么待尽调核实版，也不要写初稿，我们自己知道是初稿即可。」。版本与状态是内部的事，客户看到的就是一份正式报告——文件名用干净项目名（如 `XX项目可行性研究报告.docx`），封面不挂版本。

**9b. 「文件保存了」≠「已交付」**——把修订稿写到磁盘/知识库≠交付，用户/客户**手机端看不到**。必须通过飞书 im/v1/files + im/v1/messages API 真正发到聊天框（MEDIA: 路径文本 ≠ 真发送），`code==0` 且有 `message_id` 才叫真发出去。工具：`skills/feishu-automation/feishu-file-delivery/scripts/send_feishu_file.py`。

**9c. 先锁定自己在链条里的角色，别把「对齐修订」做成「投值研判」**（用户 2026-09-09 连续两次纠正，最高优先）——收到客户回传的 docx 时，**第一步不是读内容下价值判断，而是先分清我是谁**：①我是**这份报告的承接方/编写方**，客户只改了概述/某章、让我把整篇对齐到它、逻辑通就回发→这是**机械一致性对齐**，不是审项目值不值得投；②我是**投资者/尽调方**，客户拿项目来问能不能投→才用政治+资本双光做投值研判。**同一份可研报告，两种角色任务完全不同**：角色①做对齐（三分类保原值），角色②做评判（找硬伤/风险/漏洞）。全篇对齐任务里，客户是不是会刊、概概述是否自相矛盾、项目方有没有钱、是不是叙事型报告——**这些评审判断一律不做**，做了就是「想太多」、把用户要的活儿干偏了。用户原话「你先定位清楚…就是…对齐一下上面的东西就行了嘛，逻辑关系说得通就OK了…你不要想太多」——**收到客户改过的概述+一句「对齐一下」，默认走角色①，不该也不许升级成角色②的投值审查**（除非用户明说「审/评/把关这个项目」）。

## 新增核心规则
**客户回传 docx 让「对齐/改一下」时，先确认 `交付对象是谁` + `我处于链条哪一环` 再动手。** 只有当交付对象是**投资者/用户自己要投**、且明确「审/评/把关」时才做投值研判；交付对象是**客户**、指令是「对齐概述/逻辑理顺/回发」时，只做一致性对齐。方向错了=后面全部白干+烧对双方时间。

### ⚠️「能改的」vs「不能编的」边界（决定修订能交付多干净）
收到评审后修订报告时，先分清两类问题，**只改第一类，第二类绝不造假**：
- **A. 可编辑硬伤（直接改）**：表述不实（「十余年经验」未证实→加限定语/弱化；「已控制海森特」实为「拟收购」→全文改为拟收购）、投资口径打架（同一板块70.2/75.2/78-85/80多版本→统一到参数主控表）、误导性定性（「报批稿」→「评审修订稿/框架版」）。这些是**措辞+口径+定性**问题，AI 能独立修对。
- **B. 不可编造的数据缺口（绝不能填假数）**：资本金60-90亿从哪来、涉海七前置批文、完整财务测算表现值、协同IRR差值、台风预期年度损失。这些是**真实世界的尽调结果**，AI 编了就是评审最反感的「讲故事」，报批比现在更过不了。做法：在参数主控表/待补清单里**如实列出缺口+每项补齐后对财务的影响**，交回业主/尽调补数；空缺处保持「待尽调/待核实」，绝不冒充核定成果。
> 交付话术：向用户说明「文字表述我能改干净，但数字缺口是真实数据，我不能编，编了反而过不了审」——先对齐再动手，避免做成「改了文字、数字还空着」的半吊子。

## 架构（怎么写·骨架）
### 底层：发改委304号文 三大目标×七维度
发改委《投资项目可行性研究报告编写大纲》(发改投资规〔2023〕304号) 是权威标尺。三大目标=①建设必要性 ②方案可行性（要素保障/工程/运营/财务/影响）③风险可控性。七大维度=①建设必要性 ②要素保障性 ③工程可行性 ④运营有效性 ⑤财务合理性 ⑥影响可持续性 ⑦风险可控性。**每章结尾给一张能单独成立的「本章结论表」，评审按七维打勾。**

### 几十万字怎么撑起来：总报告+分册
几十万字绝不能「把话说长」（注水），必须靠产业集群的天然体量：
- **总报告**（决策层，只做决策不重复分册）：项目概况/主体/政策/总体投资/总体财务/风险/结论，通常2-3万字
- **分册**（价值深写主体）：每个独立板块一册，每册独立论证、独立测算=一个小可研，每册1.5~3.5万字
- **附表附图**：总投资估算汇总/分年度投资计划/三大表/借款还本付息/盈亏平衡/敏感性/国民经济评价费用效益流量

### 每分册「八段式」深写模板（防板块罗列注水）
九大板块不能「罗列一遍每块一两页」（那是业务介绍，不是可研主体）。每分册固定八段：
1. 板块定位与价值创造逻辑（2000字）：在集团产业链位置、为谁创造价值、怎么赚钱
2. 市场与产业环境（2000-3000字）：对外真实行业数据（标来源），不写虚
3. 产品/服务与技术方案（2000-3000字）：具体产品线/技术路线/设备选型（具体到规格/吨位/数量）
4. 建设内容与规模（2000-3000字）：分几期/用地用海/泊位库容产能具体数字
5. 选址与要素保障（1000-2000字）：用海用地岸线能耗资质人力，具体到能否落地
6. 运营模式与商业模式（2000-3000字）：怎么运营/收费/定价/客户/现金流特征
7. 投资估算与财务测算（2000-3000字）：本板块独立投资+回报+回收期+敏感性（数字先行）
8. 风险与协同（1000-2000字）：本板块风险+与其它板块协同（对外第三方买单）
> 每板块有真实技术/产业链/护城河/规划规模/投资测算，写2-3万字就是「自然厚度」，不需凑字数。

## 投行级算账（算账魂）
- **总投资** = 建设投资（工程费用+其他费用+预备费）+ 建设期利息 + 流动资金；预备费=基本(5-10%)+涨价预备费；流动资金可扩大指标法(按营业收入/经营成本×10-20%)
- **基准参数**：财务基准收益率 ic（产业类8-10%/基础设施6-7%）；社会折现率 is=8%；计算期=建设期+运营期（海洋重工建设3-5年+运营15-25年）
- **三级内部收益率**：项目级(全投资/融资前)、资本金级(融资后/含杠杆)、股东级——区分「项目赚钱」还是「股东赚钱」
- **关键指标**：财务内部收益率、财务净现值、投资回收期(静态/动态)、总投资收益率、资本金净利润率、偿债备付率(≥1.3)、利息备付率(≥2)、资产负债率
- **盈亏平衡**：BEP(产能利用率%)=固定成本/(收入-可变成本-税金)；达产年应≤55-70%
- **敏感性**：双因素(价格×销量)+三情景(基准/最不利/乐观)+蒙特卡洛求违约概率；落点是偿债备付率和违约率，不只看净现值
- **资金链压力测试**：滚动现金流、流动性拐点、现金覆盖月数≥3-6月、三层压力情景（建设期延误/台风×销售腰斩/融资成本跳升）
- **国民经济评价**：用影子价格算经济净现值/经济内部收益率/效益费用比
- **三表勾稽**：项目投资现金流量表/资本金现金流量表/利润表+财务计划现金流量表/借款还本付息表 六表联动、共享同一套驱动假设，两行恒等校验（资产=负债+权益、期末现金=期初+三大现金流）
- **税负红利**：涉农(海水养殖减半/农产品初加工免征)+西部大开发15%(到2030年底，20年现金流后段须回归25%)+绿色债券贴息；涉农与西部15%可能不可叠加，需核实
- **板块协同抵销**（集群可研本质分水岭）：九大板块互相供产销，必须做分部报告+内部交易抵销表（用独立第三方价作转移定价，防利润重复计算）；协同只认「对外第三方买单」，设上限(总收入8-12%取孰低)

## 涉海专项（海洋/港口/养殖类项目必有）
- 涉海七前置单列：海域使用论证、海域使用权证、海洋环评、海洋生态红线、海洋功能区划、倾倒许可、海洋灾害（台风/风暴潮/赤潮/溢油）——陆上项目没有，漏掉=后期无法推进
- **围填海管控红线（涉海最高等级，必须单列专项）**：正确文号=**国发〔2018〕24号**《国务院关于加强滨海湿地保护严格管控围填海的通知》（配套自然资规〔2018〕5号、7号）。要点：除国家重大战略项目外全面停止新增围填海审批；历史遗留须生态评估+处置到位；本项目须明确是否涉填海、优先用「不填海」集约用海/离岸构筑物方案。⚠️审核模型可能记成183号，实际是24号。
- 海洋装备用经济寿命+低残值（海工装备15-18年、船10-15年、残值3-5%甚至趋近0），别用会计折旧年限（会减值失真）
- 台风预期年度损失 AAL=Σ(超越概率×单情景损失)，用极值分布；保险转移60-70%剩余自留
- 海域使用权可抵押=核心增信资产；贷款期限必须≤用海期限-缓冲
- 海域使用金按用海方式分档（养殖年缴/填海一次性/调整系数），离岸、人工鱼礁等有省钱筹划点

## 专业Word排版（怎么做·门面）
参照 GB/T 9704-2012 公文标准 + 投行研报惯例，可执行到每一步：
- **中西文双字体**：正文中文宋体+西文Times New Roman（数字/单位用Times）；标题黑体；一定要在样式里把中文字体(eastAsia)和拉丁字体分栏都填，否则数字跑字体乱码
- **页面**：A4，上2.54/下2.54/左3.0/右2.2cm，装订线左0.5cm
- **标题体系**：章=黑体三号16pt加粗左对齐；节=楷体/黑体四号14pt；条=黑体四号14pt；正文=宋体四号14pt、行距固定值22磅、首行缩进2字符、两端对齐
- **页码分节**：封面无页码/目录罗马Ⅰ-Ⅱ-Ⅲ/正文阿拉伯1起，各节**断开「链接到前一节」**（否则页码连号无法重排）
- **专业三线表**(投行booktabs式)：顶底线1.5磅/栏目线0.75磅、**无竖线**、表头浅灰底纹+跨页重复表头、数字右对齐、表题在表上方、自动编号「表X-X」
- **图**：矢量/高清≥200DPI、图题在图下方、上下型排版、不跨页悬空、自动编号「图X-X」
- **公式**：Word公式编辑器OMML(Alt+=)原生、独立公式居中+编号右对齐（用1行2列无边框表格实现）、正文交叉引用
- **标题/目录**：标题用Word样式(标题1/2/3)+大纲级别→自动目录+自动编号+交叉引用，全书Ctrl+A→F9全更新
- **字体嵌入**：文件→选项→保存→嵌入，防换机乱码；最终导出PDF
- **30万字组织**：分章独立生成→主文档+子文档合稿→统一编号→分节页码→域更新→导出

### ⚠️ python-docx 排版引擎两处必踩 bug（2026-09-07 实测，写引擎前先看）
用 `排版引擎.py`（python-docx）跑 25 万字合稿时，**引擎自身有两个会报错的坑**，不修生成不了 Word：
1. **`set_run_font` 里的占位垃圾行**（`rPr.rFonts.rPr  # no-op` / `rPr.rFonts  # placeholder`）→ `AttributeError: 'CT_Fonts' object has no attribute 'rPr'`。**直接删掉这两行**，只保留 `rFonts.set(qn('w:eastAsia'),cn) / w:ascii / w:hAnsi` + `font.size/bold/color`。
2. **表格读取循环用了已关闭的文件句柄**（外层 `with open(...) as f` 读完 `lines=f.readlines()`，表格收集循环里却 `f.readline()`）→ `ValueError: I/O operation on closed file`。**改成索引遍历**：`idx=0; n=len(lines); while idx<n: line=lines[idx].rstrip(); idx+=1`，表格收集也用 `lines[idx]` + `idx` 自增，绝不直接读文件流。

这两处修好后，`add_heading`/`add_three_line_table`/`add_para`/`embed_fonts` 已可用（本会话跑出 2792 段落/130 三线表/340KB Word）。完整可用的引擎结构 + 2 万~30 万字分章合稿法见 `references/docx-generation-engine.md`。

### ⚠️ 第3个必做需求：让 Word「左侧导航窗格」显示章节目录（用户 2026-09-07 明确要求，勿漏）
用户打开 Word 后看左侧「大纲/导航」窗格显示「暂无设置标题」——因为**手动加粗的普通段落不会被 Word 识别为标题**，只有设置了**大纲级别 outlineLvl** 的段落才会出现在左侧章节树里。这在交付检查里是个硬需求（用户要看目录树点着跳），不加=没做对。

python-docx 落地（`add_heading` 里每个标题都调一遍）：
```python
from docx.oxml.ns import qn
from docx.oxml import OxmlElement

def _set_outline_level(p, level):
    """level1→0(标题1), level2→1(标题2), level3→2(标题3)"""
    pPr = p._p.get_or_add_pPr()
    for el in pPr.findall(qn('w:outlineLvl')):
        pPr.remove(el)
    ol = OxmlElement('w:outlineLvl')
    ol.set(qn('w:val'), str(level - 1))
    pPr.append(ol)
```
这样 Word「视图→导航窗格」左侧就会生成可点击的章→节→条目录树（本会话产出：标题1级17/标题2级109/标题3级544）。**记住：大纲级别 ≠ 加粗。普通段落加粗再多，左侧导航窗格永远是空的。**

## 生产方法（怎么组织写几十万字）
- **并行生产+主脑汇编**：单个会话写不完几十万字。拆成N个独立生产任务派pro主笔并行写（每任务一章或一分册），全部完成后主脑统一汇编成Word。
- **pro主笔设置**：`hermes config set delegation.model <pro-model> --profile default`（注意：不带`--profile`会默认写进`profiles/<name>/config.yaml`，要改主脑必须加`--profile default`指向主config.yaml）。这是运行时配置，不是靠改config文件（config受安全保护拒绝直接写）。
- **先搭施工蓝图**：完整目录树+字数分配表+参数主控表(Input Sheet)，让用户确认后再铺正文。参数主控表=计算期/基准收益率/税率/折旧/价格/利率/资本金比例唯一设源，防「数据打架」。
- **数字先行**：每部分先算投资估算+三表+指标，再围绕数字写分析。数字有了文字才有血有肉。

### 分册/章生产后「汇收割获」模式（并行产出的落地闭环）
delegate_task 的子代理写完一章/一分册后，会**把它当成 markdown 写到 `<KB_PATH>` 根目录**（而非项目目录），且**返回体是单行 JSON**——直接用 read_file 读会失败/读不全。正确做法：
1. 用 `execute_code` 读子代理 summary 缓存文件（`...\delegation\subagent-summary-*.txt`），`json.loads` 提取各字段内容（可能是单行超大JSON，read_file 会被单行卡住）。
2. 拼接所有字段 → 写入项目目录对应章节/分册文件（如 `中卷-九大分册\分册0X-XX.md`）。
3. 清理 <KB_PATH> 根目录的临时 .md（子代理写在那），避免残留重复/版本混乱。
4. 去重：子代理可能重写同名文件，执行前先删旧版，保留 pro 产出的完整版。
5. 每一步后统计项目目录累计字数，对照目标（如25万字）跟踪缺口。
> 生产节奏：pro 主笔写 2-3.5万字的单册约需 5-15 分钟；`max_concurrent_children: 3`，一批派 3 册并等待全部完成再派下一批，不要同时在跑超过 3 个（会排队/超时）。
