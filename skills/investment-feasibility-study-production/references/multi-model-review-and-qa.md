# 多模型真实审核 + 常见审核硬伤（交付前强制）

> 本文件积累「投行级可研」交付前的多模型审核纪律 + 两份真实模型审核（豆包/智谱）实际揪出的可复现硬伤清单。写报告时就要预判这些，别等审核才暴露。

## 一、多模型审核纪律（用户钦定偏好，必须遵守）

1. **用真实聪明模型，不是主模型pro冒充**。用户原话质疑「审核他们真的在用Kimi和豆包的聪明模型在做吗？」——delegation主模型是pro时，派出去的审核任务会继承pro，**不是用户要的分析助手**。审核前必须把 delegation 切到真正的审核模型。
2. **delegation是全局单模型配置**，一次只能指一个模型。要「豆包+千问/Kimi」多个模型，需逐个 `hermes config set delegation.model <model> --profile default` + `hermes config set delegation.provider <provider> --profile default` 切换到目标，再派单，再换下一个。
3. **派单前先测key可用性**（直接urllib/dashscope/ark/zai端点发一个chat请求）：
   - 豆包(ark)：`https://ark.cn-beijing.volces.com/api/v3/chat/completions`，正确model id=**doubao-seed-2-1-turbo-260628**（config常写成不含编号的`doubao-seed-2-1-turbo`会404）。key明文在config。
   - 智谱(zai)：`https://open.bigmodel.cn/api/paas/v4/chat/completions`，**glm-5.2免费可用**（第1梯队最聪明），可作豆包/千问的替代视角。
   - 千问(dashscope)：`https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`，**免费额度易耗尽**(403 Free quota exhausted)。
   - Kimi(kimi-coding)：`https://api.moonshot.cn/v1/chat/completions`，**key易401失效**（需充值）。
   - 失效的补一个可用免费聪明模型（glm-5.2），不要空着。
4. **审核任务必须明确「通读全部全文，不许只抽查」**。主报告=总报告N章+九个分册，通常在项目目录拆成14个md。子代理默认偷懒只读前几个分册，要用steer强制读全（列出每个文件名+路径）。子代理可能在steer送达前就完成了（missed_steer），此时依赖它初始任务书就把「全部通读」写进去。
5. **审核分工互补**：一个偏银行审贷官/风控（财务勾稽/可复算/数据可靠性/排版），一个偏产业投资分析师（研判逻辑/市场机会/商业模式/风险）。避免两人读同一批分册浪费。

## 二、常见审核硬伤（写报告时预判，审核时重点查）

### 致命级（评审直接判「不能交付」）
1. **投资重复计算**：多个分册把同一笔投资都算进去（实测：分册01「海上加注船队45亿」和分册02「供油船队45亿」重复；码头也重复）。同一资产必须明确归属唯一分册，用合并抵销表核对。
2. **总报告板块命名 vs 分册命名不一致**：总报告写「海洋金融/海工重工/蓝色粮仓」，分册写「观光低空/海洋食品/资产管理」——命名体系、板块划分对不上，一核对就穿帮。**总报告与分册用同一套板块名+编号**。
3. **主体身份自相矛盾**：既说「未来成立的项目公司」又写「十余年运营经验」。区分已有控股主体 vs 拟设立项目实施主体。
4. **投资构成严重缺失**：300亿里64.6%标「待尽调」，可研核心要素不成立。给每板块投资量级区间（即使是宽区间），别全行留白。
5. **财务指标全空**：无一组内部收益率/净现值/回收期/偿债备付率实测值，却已下「可行」结论。至少给基准情景的区间值（注明「基于现有参数的区间估算，正式值待参数主控表核定」）。
6. **资本缺口未闭环**：注册资本3亿 vs 总投资300亿，287亿缺口没说清怎么补。给资本金到位路径（增资/战略投资者/产业基金分阶段）。
7. **涉海前置逻辑断裂**：用海/围填海/岸线审批全「待尽调」却已判「可行」。结论改为「条件性可行（以涉海前置要件取得为前提）」，风险矩阵中涉海审批评审级别应调高。
8. **分册以JSON原始格式嵌入正文**：某分册写成`{"分册04":"# ..."}`导致内容不可读（markdown误存成json）。合稿时用execute_code `json.loads`提取再落成标准md。

### 重大级（体现不专业，要提前处理）
- 建设期/运营期/资本金比例在各分册口径不一（建设期5-8年/3年/2-3年混用、资本金20-30%/30%/40%冲突）→ **参数主控表是唯一设源，各分册只引用**。
- 板块业务重叠（渔品收储/海产汇通/海洋食品三板块均涉收储冷链加工贸易=内部同业竞争）→ 总报告加「九大板块业务边界与分工矩阵」。
- 银行/金融牌照未论证路径（把「海洋银行」当商业模式核心环节却不证牌照可行性）→ 改用「海洋金融事业部/产业金融服务平台」保守口径，单列金融牌照路径论证。
- 数据陈旧（2023数据用于2026可研）→ 用最新年份官方数据。
- 单价/造价无出处（岸线45万/米、油库25.2亿）→ 标询价/造价依据。
- 各分册称「独立可存活」但板块依赖度极高 → 补「无协同情景」独立测算。

### 一般级 / 建议级
- 「十五五规划」等引用应标具体文号；待尽调事项过多的分册给量级区间；补竞争格局定量分析、内部交易定价基准、投资优先级/分期额度表。

### 评审模型自身也会写错——文号必须二次核验（本能反应）
审核模型**自己也会把文号记错**。实测：豆包模型说围填海管控文件是「国发〔2018〕183号」，实际正确文号是**国发〔2018〕24号**《国务院关于加强滨海湿地保护严格管控围填海的通知》（配套自然资规〔2018〕5号、7号）。**任何审核报告里引用的政策文号，落地进报告前一律 web_search 二次核验**——评审提缺失是功劳（它说「漏了围填海专项」是对的），但它给的具体文号可能错。核验确认后再写，否则把错的文号写进正式报告=新的硬伤。

## 二·补：总投资口径对账（客户给整数的场景）
当客户给一个干净整数（如「总投资300亿」）而九大板块估算合计对不齐时，不要生硬凑整、也不要全行留白。采用**两段口径对账**：
- **300亿 = 九大板块工程直接投资（客户口径）**，逐板块给量级/区间（已框定的用客户数字，待尽调给宽区间），合计可落在整数下方留合理浮动（如287亿，留约10亿浮动空间）。
- **配套资金另行单列**：预备费(约5%)+建设期利息(约6%)+流动资金(约5%)≈工程投资的15%，作为「资金总需求」的追加项披露，不塞进300亿口径里。
- 这样既对齐了客户「300亿」的直觉，又守住建投行「总投资=建设投资+建设期利息+流动资金」的专业口径，还不逼着自己对每笔投资拍脑袋凑数。

## 投资边界划分表（消除分册重复投资的落地方法）
审核揪出分册间重复投资后，**建一张「总报告-分册投资边界划分表」**：明确每项资产唯一归属一个分册（实测：加油船队45亿归分册01海洋能源，分册02船舶重工剔除；码头岸线16亿归分册02）。判定原则=「一项投资只归一个板块、不重复计列」。改分册自身表时同步改：核心指标速览表、分年度投资计划表、投资估算表、贷款规模、建设期利息——全册口径一致，否则改一半留一半还是硬伤。

6. **深调后交叉核验（改完全文再出稿）**：审核→修订→改完全文后，用 execute_code 全局扫描一遍再做校验：①英文残留（`re.findall(r'\b[A-Za-z]{2,}\b')` 排除md/http等，应≈0）②JSON转义残留（`txt.count('{\\"')` 应0）③关键文号出现次数（如`国发〔2018〕24号`≥1）④各分册投资口径与总报告一致（无遗留的旧投资额，如分册02的135/120应清零）⑤大纲级别已写入（统计 outlineLvl 各层数量，标题1/2/3级都有值）。上述全过再交付。

## 二·补2：多模型直连API审核的工程实现（22万字级 · 2026-09-08 实测通过）
> 大报告的多模型审核不一定要走 delegation 子代理（子代理继承pro、且把全文塞子代理会撑爆上下文）。**更稳做法=直接用目标模型的 chat API 送全文**，两个模型并行跑，各自把审核报告落盘。适合「总报告+九分册≈22万字」这类单次可送全文的量级。

### 工程要点（踩坑实录，勿再踩）
1. **送全文而非拆块**：22万字≈15-16万 prompt token，Kimi k3 / qwen3.8-max / glm-5.2 都收得下。用合稿 md（含表格）作为 user 消息，system 里给分级审核指令。一次送全文=模型能看到跨分册一致性（投资重复/口径矛盾），拆块反而漏掉关键的跨分册硬伤。
2. **Kimi 答案在 reasoning_content、content 常为空**：`msg['content']` 可能空串（推理占满max_tokens），**必须 `if not content: content = reason` 兜底**。且 Kimi 要 `temperature=1`。
3. **max_tokens 要给足**：Kimi 用 8000 会被推理截断（上一轮 content=0、reason 只到一半）。送 20000 才拿完整。其它模型 14000-16000 够。
4. **>300s 任务不能用 execute_code**（硬超时杀kernel），必须 `terminal(background=true)` 跑独立 python 脚本。脚本内用 `threading` 并行两个模型，各自 `open(...).write()` 到独立文件（`kimi_review.txt` / `qwen_review.txt`），这样即使一个超时另一个结果仍在。
5. **⚠️ background 命令里别再加 `&`**：`terminal(background=true)` 再在命令末尾拼 `&` 会**双重后台**（bash no job control），python 实际没跑、日志空。正确=`command: cd ... && python -u run.py > log 2>&1`（**-u 强制无缓冲**，能看到实时输出），再 `process_manage action=wait`。
6. **被 wait 卡住就检查中间产物**：`for f in kimi_review.txt qwen_review.txt review_results.json; do ls -la $f; done`——部分结果仍落盘，别只看日志。
7. **两模型分工互补**（前面说了）：审贷风控（Kimi）+ 产业研判（千问）。**千问偏判「定性与定量的落差」**（方法论框架完整、数据实质不足），**Kimi 偏掘「算数勾稽铁证」**（资本金54+贷款50=104≠86.3亿、收入/投资3.7%却称IRR 9-11%）。

### 三模型交叉 → 「总修改清单」
三个模型各自落盘审核报告后，**人工/主脑交叉比对**，标 ★共识（三方都提）与单方独见，再合并成一份「总修改清单」（致命/重大/一般/建议四级），落盘 `06-审核意见/00-总修改清单-三军交叉审核.md`。共识=最稳的硬伤；单方独见也可能站得住（如 Kimi 掘出的算数矛盾常是别人漏的）。

### 报告lab PDF 生成（金色系）注意
`reportlab` 这个版本**不支持 `<span style=...>`** 内联样式，报 `findSpanStyle not implemented`。用 **`<font color='#C9A227'>...</font>`** 替代；表格字体调小到 11.5-12.5pt（14.5 会挤爆）。

## 三、审核交付动作
- 每个审核报告独立落盘到项目目录 `06-审核意见/`（如`智谱模型(glm-5.2)-严格审核报告.md`），留着审计痕迹。
- 合并多份审核报告成一份「总修改清单」（按致命/重大/一般/建议分级），给用户过目，逐条修订后再排版交付。
- 主报告文件落地目录：`<KB_PATH>`，含`00-报告施工蓝图.md`、`上卷-总报告/`、`中卷-九大分册/`、`排版引擎.py`、`00-合稿-*.md`、`05-尽调资料/`、`06-审核意见/`。
