# 设计说明与实战依据

## 为什么需要“每个 profile 一个浏览器”

不配 `browser.cdp_url` 时，Hermes 的浏览器能力会**按任务临时起实例**：
- 临时目录 `%TEMP%/agent-browser-chrome-<UUID>`，任务结束不一定回收 → 孤儿堆积
- 每次新目录 = **没有登录态**（要重新扫码/登录）
- 多个 profile 同时干活 → 多个实例抢焦点、抢屏
- 用户抱怨“AI 一干活我的浏览器就被抢走”

配了固定实例后：固定 user-data-dir（**登录态长期复用**）+ 固定端口 + headless（**不抢屏**）。

## 关键事实（实测/源码确认）

| 事实 | 说明 |
|---|---|
| `browser.cdp_url` 原生支持 | Hermes 内置 CDP 支持；连上即用，不再本地 launch |
| **热生效** | 每次调用重读 config（`_browser_cfg` 无缓存）→ 改完不用重启网关 |
| 官方默认无头 | `browser.headed` 默认 `False`；源码注释：*“Headless by default (a focus-stealing window defeats a background capability)”* |
| 连不上不降级 | 解析到 cdp_url 后跳过本地 launch → 实例死了任务直接失败（所以要挂探活） |
| 登录态在 user-data-dir | 认领既有实例**只改端口登记、不动目录**，登录态保留 |

## 验收判据

**不要**只看命令行有没有 `--headless`：
- renderer/GPU/utility 子进程不带该参数
- 实例可能被别的机制以有头模式拉起（启动脚本写了 headless ≠ 当前进程无头）

**要**枚举屏幕上真实存在的窗口，按 PID 归属到各实例，判据 = **后台型实例可见窗口数 == 0**。

## 实战数据（Windows 11 / 4 个成员实例 / 2026-09）

| 阶段 | 进程 | 内存 |
|---|---|---|
| 未隔离（每任务临时实例堆积） | 203 | 8508 MB |
| 回收孤儿后 | 89 | 5127 MB |
| 统一无头 + 固定实例 | 71 | 2508 MB（Agent 实例 722 MB） |

- 4 个 Agent 实例：38 进程 / **722 MB**；其余浏览器（Chrome+Edge）：26 进程 / 1785 MB（**别把全机总数都算到 Agent 实例头上**）
- 可见窗口：Agent 实例 **0**，屏幕上另外 2 个窗口均属其它程序

## 频率建议

- **探活 + 孤儿回收**：30 分钟（管可用性与内存；实例死了成员任务会失败）
- **防抢屏审计（`--enforce-headless`）**：**每日一次**（无头是默认值，出现可见窗口属罕见异常，日频兜底足够；高频纯浪费）

## 多实例并存的内存账（估算）

单个无头 Chrome 实例约 200-900MB（取决于打开的页面数与站点复杂度）。N 个成员就多 N 份。用户侧想省内存：`stopall` 一键全部释放，要用再 `start all`（秒级回来，登录态不丢）。
