# 子代理派工规范

## When to Use
- 即将调用 `delegate_task` 写任务之前（定 goal/context）
- 子代理刚返回，要判断成果能不能直接交给老板之前
- 子代理空手/超轮次返回，决定要不要再派之前

主脑统筹制（SOUL / TEAM-PROTOCOL.md）规定重活必派子代理、主脑只做统筹；本技能管**怎么派才能拿回真成果**，以及成果回来后怎么验收。

## 派工时：写 goal/context 的三要素
1. **给精确输入清单**——文件路径、URL、关键词、已验证的访问方式（import 路径/命令），把子代理的"自行探索"压缩到零：摸目录、试工具是轮次额度的最大耗材
2. **要求边做边落盘**——每完成一步就 write_file 写到 scratch；成果只存在子代理内存里的话，轮次一耗尽全部归零（空手返回的标准剧本）
3. **只要结论+产物路径**——大输出先落盘再筛，禁止回灌原文大段内容

## 派工后
- 回老板一句"已派出（谁在干什么）"立刻结束回合，禁止在主脑里干等
- **空手即止损**：返回空手/超轮次上限 → 先判是不是空转（见验收门）。真干不动（活太大）可缩小任务、带精确输入清单重派**一次**；再空手就自己干——两三轮能收的活，派工反而更慢。**空转不重派**，直接降级。

## 验收门（交付老板前必过）
- 自报"未验证/未联网/推断得出"的调研报告 = 半成品：关键结论自己实测复核后才交付，并在报告里区分「已核验/存疑」
- 报"成功"但给不出可核验产物（文件路径/URL/原文数字）→ 按失败处理
- **产物路径必须 `ls -l` 实测回读**：子代理会报出一个根本不存在的文件路径，`test -e` 不过即判失败，不得凭自报交付
- **返回只有十几秒、max_iterations 耗尽且一次工具都没调 = 空转**——不是任务太大，是子代理没动起来，按下面的降级路径自己干
- 数字与事实必须来自原文，缺的写"未获取到"，绝不编造

## 空转的降级路径（调研 / 批量检索类）
不要重派，直接用 `execute_code`：一次调用里循环 `web_search`（8~10 条查询）→ 再一次 `web_extract` 抓 3~4 篇原文 → `write_file` 落盘。三轮工具调用即可拿回带来源的成品，比派工快且结果可验。完整取数→成文→验收流程见 `knowledge-base-research`。

## 分工边界
- 扫描/批量检索类活归「脚本+后台进程」，不派子代理（做法见 email-manager 技能里的邮箱挖掘流程）
- 需要问老板的活不派（子代理没有 clarify）
- 不可逆副作用、需老板交互的步骤留在主脑
