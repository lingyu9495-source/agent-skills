# 跨框架智能体迁移 — 详细清单

适用：把一个已在跑的 Hermes 智能体搬到另一套智能体框架（QwenPaw、或其他自托管框架），或反向迁回。
目标不是复制目录，而是**在目标框架里重建出一个身份、记忆、能力都对得上的智能体**，然后一刀切换。

---

## 1. 先审目标框架（动手前必答的 7 问）

每问都要官方文档原文 + URL；查不到就标「未证实」。**禁止凭印象填答案**——把猜测写成结论，后面整份迁移方案都建在沙上。

| # | 问题 | 为什么决定方案 |
|---|---|---|
| 1 | 部署方式与常驻方式（pip / 一键脚本 / Docker / 托管）；运行时版本要求；工作目录与密钥目录 | 决定目标机怎么装、数据放哪、怎么开机自启 |
| 2 | IM 渠道接入：是否支持自建应用 App ID/Secret；**长连接还是 webhook 回调** | 长连接 = **不需要公网回调地址**，现有 App 可直接复用；webhook = 要改 IM 后台回调 URL |
| 3 | 多智能体隔离：能否跑 N 个独立 agent，各自独立工作区/配置/记忆/技能 | 决定「N 个智能体各挂一个机器人」是否原生可行 |
| 4 | 技能格式与目录；能否识别 SKILL.md（YAML frontmatter + markdown） | 决定技能是搬、是改、还是重写 |
| 5 | 定时任务格式、cron 表达式、**投递目标能否指定到某个 IM 会话或文件** | 决定每日产出类任务能否重建 |
| 6 | 记忆机制：存哪、什么格式、**能否导入外部 Markdown** | 决定记忆是导入还是重灌 |
| 7 | 模型接入：第三方 OpenAI 兼容端点怎么配（提供商 → base_url → API Key → 模型 ID → 设默认） | 决定原模型的 key 与端点能否继续用 |

**核实纪律**：技能与配置的具体字段、目录结构，优先抓目标框架的**内置样本**（初始化产物、内置技能池原文、GitHub docs/源码 raw 文件），而不是隔着文档猜。文档没说清的，等目标机装完直接看它生成了什么，照样本改写。

---

## 2. 源资产四分类盘点

要求：每一项给出**文件路径 + 实际计数**（用 terminal 跑 `wc`/`du`/`grep` 统计，找文件用 search_files 而非 `ls`），产出映射表。

| 分类 | 典型内容 | 处理 |
|---|---|---|
| 【直接搬】 | 纯知识型技能（无路径/CLI 依赖）、知识库 md、人格正文 | 原样投放到对应位置 |
| 【需改写格式】 | 人格/记忆 → 目标框架 persona 与记忆字段；技能 → 目标框架技能格式；任务 → 目标框架 cron 字段 | 逐项转换，注明转换规则 |
| 【需重建】 | 渠道凭证、定时任务、共享层挂载、密钥托管 | 在目标框架里重新配置 |
| 【无法迁移】 | 会话状态库、框架专有运行时、随 profile 落的二进制依赖副本 | 明确丢弃，或导出为文本留存 |

**体积规律（实测口径）**：一个 80MB 级的 profile 目录，净迁移量常在 10MB 上下——`bin/`（框架运行时副本，几十 MB）、状态库+wal、`logs/`、`cache/`、`state-snapshots/` 占绝大部分；真正的灵魂（SOUL + 记忆 + 知识 + 任务定义 + 配置）往往**不到 100KB**，体积大头几乎全在技能库。先分类，别整目录传。

历史归档目录（`skills-archive/` 之类）默认不迁，按需回捞。

## 3. 打包命令（软链必须展开）

```bash
D=~/projects/<proj>-migration; mkdir -p $D
cd ~/.hermes/profiles
tar -czhf $D/assets-<names>-<YYYYMMDD>.tar.gz \
  --exclude='bin' --exclude='logs' --exclude='cache' --exclude='state-snapshots' \
  --exclude='sessions' --exclude='state.db*' --exclude='gateway*' --exclude='*.bak-*' \
  --exclude='skills-archive' --exclude='.curator_backups' --exclude='backups' \
  <p1>/SOUL.md <p1>/USER.md <p1>/profile.yaml <p1>/memories <p1>/skills <p1>/cron/jobs.json <p1>/.env <p1>/config.yaml \
  <p2>/SOUL.md <p2>/profile.yaml <p2>/memories <p2>/skills <p2>/knowledge <p2>/.env <p2>/config.yaml
```

- `-h` 不可省：跟随软链把技能实体打进去，否则对方拿到断链包。
- 打完后验条目：`tar -tzf <包> | awk -F/ '{print $1"/"$2}' | sort | uniq -c`，确认各项都进去了。
- 含密钥的文件（`.env`、`secrets/`）是否随包传，按交付通道决定；**走 SSH 直传比落 tar 包再转存安全**。

## 4. 各类资产的落位映射（通用骨架）

| 源 | 目标框架里的对应物 | 迁移要点 |
|---|---|---|
| 人格文件 / 身份说明 | 系统提示 / persona 配置字段 | 身份锚定段（「我是 X，不是 Y/Z」）必须原样保留，这是防混同的根 |
| 记忆文件 | 目标框架记忆库，或注入人格的静态段 | 体量极小；若目标框架无外部 Markdown 导入，直接作为初始记忆灌入 |
| 技能库 | 目标框架技能目录（自有格式） | 逐个判定「直接搬 / 改写 / 砍掉」；含框架专有命令的先砍 |
| 定时任务定义 | 目标框架定时任务 | **两处都要清点**：profile 自有 + 别处代持的 |
| IM 凭证与 home channel | 目标框架渠道配置 | 长连接方式下 IM 后台不用改回调，只需启用机器人能力 + 订阅「接收消息」事件 |
| 共享层（团队记忆总部 / 共享技能目录） | 目标框架的等价共享机制 | 没有对应物就记为「迁移后失效项」 |

---

## 5. 切换与验证时序

1. 目标侧：装好 → 配模型与渠道 → 建出 N 个独立 agent → 灌人格/记忆/知识 → 挂回定时任务。
2. **先验静态**：agent 能起来、技能能被识别、模型连通。
3. **再验交互**：让每个智能体在 IM 里自报家门（身份对不对），发一条真消息走通回程。
4. **一刀切**：旧机停 → 新机起。同一个 IM 应用不能被两套框架同时接管（长连接互抢），**切换前明确告知老板会有几分钟机器人不响应**。
5. **次日回查**：定时任务的产出文件（日志/沉淀 md）当天有没有新行。
6. 旧机按退役 SOP 处置（停服务、禁自启、归档改名、断链扫描）。

---

## 6. 需要提前备好的交付物

- 投放物料包（tar，软链已展开）+ 一张「源 → 目标」映射表给老板过目。
- 待老板拍板的口径清单（迁移时机 / 是否复用 IM App / 模型走哪个 / 旧机何时退役）——一次性问清。
- 目标机由他人部署时，向对方索取：公网 IP、SSH 登录方式、目标框架工作目录、控制台访问方式。
- 给部署方的防返工提醒：控制台别裸奔公网端口、机器要能出网访问 IM 开放平台域名、每个 agent 独立 workspace 别都塞默认 agent。
