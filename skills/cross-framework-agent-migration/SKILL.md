# 跨框架智能体迁移（换壳不换魂）

## When to Use（触发条件）
- 把一个已在跑的 AI 智能体从一套框架搬到另一套（如 Hermes → QwenPaw / 其他自托管智能体框架），或反向迁回
- 换服务器同时换框架。注意：同一框架内的 profile 搬家、改名、退役走 skill `agent-lifecycle-ops`，不走本技能
- 老板拿着某个框架的测评/教程/开源项目来问「要不要把 X 搬过去」「能不能把你搬到 X 上」——**先走下面的第 0 步决策，别直接进 SOP**
- 老板问「我有这几个框架和工具，怎么规划 / 用哪个当第一大脑」——这是选型问题不是迁移问题，走下面的「回答姿势」一节，**别直接开始部署**

## 核心铁律
**迁的是灵魂，不是身体。** 目标框架没有源框架的 profile / SKILL.md / 状态库结构，目录搬过去也跑不起来。要迁的是：人格与身份、记忆、知识、任务定义、渠道凭证。其余全部重造。

排序不可反：**先审目标框架能力 → 再盘源资产 → 打包 → 重建 → 切换**。反过来做会先搬一堆带不动的东西。

## 第 0 步：先判断「值不值得迁」（老板问「要不要搬过去」时必过）
用三条筛，任一条严重不过就别迁：

1. **交互面能不能保住**（最硬的一条）：源智能体的价值有一半在「老板怎么找到它」。有 IM 网关的框架（Hermes/飞书）换成只有本地 Web 工作台的框架（DSH 等），等于把「手机上随手聊」降级成「开电脑点进去」。**IM 渠道缺失 = 迁移收益基本为负。**
2. **沉淀能不能带**：人格/记忆/技能/定时任务/多智能体编制，逐项标「能带 / 不能带」。一半带不走 = 搬迁即归零重启。
3. **稳定性档位**：目标框架仍是 developer preview（官方明说会有破坏性变更）时不承接生产业务，只能当实验台。
4. **判据是「沉淀在哪」，不是「哪个更强」**：同类框架（全功能个人 agent + IM 接入，如 Hermes / QwenPaw）能力高度趋同，横向对比比不出高下——**别陪老板做能力对比表**。真该比的是**已有沉淀的体量**：技能数、记忆、多智能体编制、定时任务、渠道配置。技能若同契约可零改动搬走（见下），但**记忆 / 编制 / 定时任务 / 渠道一律重建**。给老板的类比：「这是已经装修好的房子 vs 毛坯房——技能能搬，家徒四壁。」

> **判断这类问题先算一笔数**：说出源框架上跑了几个月的实际资产（技能个数、agent 个数、定时任务条数、接入渠道数）。这些数字一摆出来，换框架的收益往往直接变负。

**多个框架并存的唯一合法姿势**：各自绑定**独立的 IM App**（同一个 App 被两套框架同时接管会互抢消息，见「时序硬约束」）。并存还要接受 N 套记忆 + N 套技能 + N 套定时任务的维护成本：**超出老板实际能维护的数量，结局就是每套都半死不活**。向老板点破：工具数量不增加产能，纪律才增加。

**过不了就改走「双栈并行」，别搬**：源智能体留任**调度中枢**（继续持有 IM 渠道、记忆、cron、团队编制），新框架作**外挂专家**只干专项重活（编码、长链报告），成果用共享工作目录交换、由中枢回投 IM。向老板一句话讲清类比：「给总经理配个专家，而不是把总经理改造成专家。」

## 回答「我该用哪个框架 / 工具」这类问题的姿势
老板会拿着一串工具名来问「怎么规划」、「用哪个做第一大脑」，并列出他「初步圈定」的清单。**先判「工具是不是瓶颈」，不要直接输出对比表**——默认情况下工具不是瓶颈（真正的瓶颈通常是产品、客户、现金流），罗列只会助长工具收集癖。顺序：

1. **先把话题拉回业务**（「下个月靠什么收钱」），而不是先比较框架优劣；
2. **盘他已有的**：他准备「安装」的工具往往早就在跑（查进程 / 配置 / 历史部署记录），**别凭印象答「没有」**；
3. **排一张编制表**：谁接活（持有 IM 渠道的中枢）/ 谁干重活（无 IM 通道的专项工具）/ 谁兜底（备用模型、已装 CLI）；
4. **点名哪个是多余的**——说得出「这个你已经有，重复了」比推荐新工具更有价值。

铁律：**每新增一个框架，维护成本是指数级的**（多套记忆、多套技能、多套定时任务、多套凭据）。评估时把「维护成本」与「产能增益」并列摆出来。

## SOP（五步）
1. **先审目标框架（7 问）**：部署方式与常驻方式 / IM 渠道接入（长连接还是 webhook 回调）/ 多智能体隔离 / 技能格式与目录 / 定时任务格式与投递目标 / 记忆机制与能否导入外部 Markdown / 模型接入。每问要官方文档原文 + URL，**查不到就标「未证实」，禁止凭印象**。
2. **源资产四分类盘点**：【直接搬】【需改写格式】【需重建】【无法迁移】，每项给路径 + 实际计数（用 terminal 跑 `wc`/`du` 统计，找文件用 search_files 而非 `ls`）。
3. **打包**：`tar -czhf` + 排除运行态，`-h` 不可省（软链必须展开）。现成命令见 `references/cross-framework-migration.md`。
4. **重建顺序**：静态资产（人格/记忆/知识/技能）→ 模型与渠道凭证 → 定时任务 → 实测 → 最后决定会话历史去留。
5. **目标框架侧照它实际生成的结构改**：装完先看它自己生成的示例技能与配置（初始化产物、内置技能池原文、源码 raw），照样本改写，别隔着文档猜格式。

## 五个隐形耦合（漏一个就是静默停摆，不报错）
- **跨 profile 代持的定时任务**：cron 常由主 profile 集中持有，任务提示词里硬编码 `HERMES_HOME=/…/profiles/<x>` 绝对路径。只迁被迁的 profile 不重挂这些任务，该智能体的每日产出与记忆追加会无声停掉。清点 cron 时要**同时清 profile 自有 + 别处代持**两份。
- **技能里的框架专有依赖**：技能正文中的 `~/.hermes` 绝对路径与 `hermes-cli`/`feishu-cli` 等框架命令，目标框架没有对应程序。
  **先判契约，再估工作量（能省一整轮返工）**：若目标框架用 **Anthropic Agent Skills 规范**（`<技能名>/SKILL.md` + YAML frontmatter，至少 `name`/`description`）——Hermes 的技能就是这套——则技能**可零改动复用**，只需把技能目录放进它的发现根（多在 `~/.agents/skills`，那是多个 agent 共读的公共根），正文一个字都不用改，也不用逐个试跑。**不是同一套契约时**，才走下面的工作量估算：**先抽 10 个高依赖技能试跑再估总量**，别拍脑袋说「技能直接搬」。
  **解法（免掉逐个改写正文）**：①正文只做**安全的路径前缀批量替换**（框架家目录/profile 目录 → 目标工作区路径，删改前先备份）；②框架专有**工具名**不要逐个改正文，改成在**每次会话都注入的身份文件**（目标框架的 PROFILE/AGENTS/SOUL 类文件）里放一张「旧名 → 本框架工具」对照表，让模型自己映射。实测=批量替换上百个技能文件 + 一张对照表，技能即可用，且新增技能也不用再维护映射。
- **共享层**：团队级技能（记忆总部、共享技能目录、共享同步 cron）指向源框架的共享资产，目标框架若无等价共享机制，这些技能会引用空路径。明确记录为「迁移后失效项」，别假装迁过去了。
- **框架能力依赖的工作方式**：SOUL 里写「重活派子代理」「主脑只做统筹」这类铁律，靠的是源框架的委派能力；目标框架若没有子代理机制，这条工作方式要重写而不是照搬。
- **IM 凭证与投递目标**：多个投递会话往往分属不同的 IM 应用，迁移后逐条重建，串了就投错群。

## 时序硬约束（切换）
同一个 IM 应用（飞书自建 App 等）**不能被两套框架同时接管**——长连接会互抢消息。切换必须一刀切：旧机停 → 新机起。
- 切换前**明确告知老板会有几分钟机器人不响应**（他会以为又挂了）。
- 长连接方式下飞书后台**不需要改回调 URL**，只需启用机器人能力 + 订阅「接收消息」事件；现有 App 可直接复用。
- 切换后**次日必须回查**定时任务产出文件（日志/沉淀 md）有没有新行——定时任务是最后一环，也最容易静默失效。
- **旧侧定时任务必须显式暂停，不是只停服务**：旧框架的 cron 独立于网关进程，网关停掉后它照常唤起智能体 → 同一份日报跑两遍、文件写回旧机，**全程不报错**。停服务 + pause cron + `systemctl --user disable` 三件一起做，且用 **pause 而非 delete** 保留回滚路径。
- **主动推消息类任务要等真实会话标识**：投递目标（`user_id`/`session_id`）必须由「已有真实会话记录」才能取到，框架无法凭空推。切完通道先让老板给每个 bot 各发一条消息，再读会话记录去建任务。
- **目标框架跑在容器里时**先查挂载表：容器 `/root` ≠ 宿主机 `/root`（agent 自己一套 `.ssh`，宿主机 root 常被挂到容器其他路径），共享目录可能已直接可见；容器默认 UTC，时区要三处一起改（容器 `/etc/localtime` + 框架全局时区 + 每条 cron 的 timezone）。容器内 agent 验证必须**在容器内**真登录一次，宿主机的成功不算数。细节见 `references/qwenpaw-notes.md`。
- **反向迁入 Hermes（目标=Hermes）的省内存真相 + 切换触发器**：Hermes 官方拓扑是**一台机一个 gateway 服务所有 profile**，新 profile 挂在同一进程、不新增进程 → 迁入即净省旧框架的常驻内存（实测 QwenPaw→Hermes 净省约 1GB）。切换时**网关进程内不能重启自己**（会被系统防护拦下）→ 用 `systemd-run` 外部计时器触发网关重启（由 systemd 发起，不经会话进程树），并先给老板一句「约 1 分钟不响应，属正常」。
- **源框架自带的身份模板不能原样搬**：源框架目录里的 AGENTS.md/SOUL.md 常是**框架自带的模板**（如 QwenPaw 的「你是 QwenPaw 内置 QA Agent」），原样搬会让新 profile 误认身份 → 迁人格时逐个核对，剔除框架模板、只留本人格；切换后让新 profile **自报家门**实测人格/记忆/模型是否都对。

## 交付纪律
- 需要老板拍板的口径（迁移时机、是否复用 IM App、模型走哪个、旧机何时退役）**一次性问清**，别中途反复请示。
- 目标机由他人部署时，向对方要：公网 IP、SSH 登录方式、目标框架工作目录、控制台访问方式；并给三句防返工提醒：控制台别裸奔公网端口、机器要能出网访问 IM 开放平台域名、每个 agent 独立 workspace 别都塞默认 agent。
- 详细清单（7 问表、四分类表、打包命令、落位映射、验证时序）见 `references/cross-framework-migration.md`。
- 迁往 **QwenPaw** 时先读 `references/qwenpaw-notes.md`（已核实的框架事实 + 迁移前必须实测的待核实项），省一轮重复调研。
- 评估/迁往 **DeepSeek Harness（dsh）** 时先读 `references/dsh-notes.md`（运行依赖与内存实测、访问令牌机制、四种模式、子代理多模型、技能扁平化软链的坑、沙箱验收四步、已定的双栈并行结论）。
