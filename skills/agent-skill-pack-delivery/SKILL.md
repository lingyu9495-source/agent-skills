# 批量技能包交付（给外部智能体配技能）

## When to Use（何时用）
- 老板要"给某个智能体 / 某个客户环境配一批技能"，要的是对方**拿去就能装**的包（不是清单）。
- 从团队技能库（知识库 总桶 + 本机 skills）里批量选出几十到几百个技能，外发给非本团队的环境。

## 第 0 步：先问框架（决定技能目录，不要白做）
Agent Skills 是开放标准（一个目录 = 一个 `SKILL.md`），同一份换框架即用，但安装目录不同：

| 框架 | 技能目录 |
|---|---|
| Hermes | `~/.hermes/skills/`（全局）或 `profiles/<名>/skills/` |
| Claude Code | `~/.claude/skills/` |
| Codex | `~/.codex/skills/` |
| DSH / WorkBuddy / 其他 | 各按自身文档（Agent Skills 兼容） |

对方框架没确认就动手，包做出来方向不对。一问即可，不是请示。

## 第 1 步：建技能索引 —— 别信 frontmatter 去重
扫全部候选目录，提取每个 `SKILL.md` 的 frontmatter name/description 建索引（`find <roots> -name SKILL.md`）。

**坑（会静默漏技能）**：
- 按 frontmatter 的 `name` 去重，不同目录的**同名技能只留一份** → 少掉一批。→ 改用**目录名**建映射。
- 知识库 里很多技能目录是**壳**：只有 `references/` `scripts/`，**没有 `SKILL.md`**；真身在本机 `~/.hermes/skills/`。→ 选定后**复制前必须校验目标目录含 `SKILL.md`**，否则打包出一堆空壳，装上去什么也没有。

先扫的 roots（按真身优先级）：本机 profile 的 `skills/` → 知识库 各成员 `技能/` 目录。

## 第 2 步：按接收方岗位分域挑选
按接收方的能力域分组挑（例：某 AI 员工 = 财税/工商/法律/HR + 文档办公 + 电脑自动化 + 联网取数 + 搜索调研 + 知识库/任务 + 沟通交付 + 自管理 + 通用工具）。清单里每项带一句说明，别只给名字。

## 第 3 步：复制 + 脱敏（外发的关键，漏了就是事故）
复制到 `deliverables/<包名>/skills/<技能名>/`，**带全 `scripts/` `references/` 子目录**。然后逐文本文件批量替换。**必清八类**（漏一类就是事故；`127.0.0.1`、`0.0.0.0`、示例 IP、`user@example.com` 无害，别误伤）：

1. **身份词** —— 内部称呼、成员花名、品牌名、对老板的称呼（换成接收方能用的通用词，如「用户」→「老板」）。
2. **IM 凭据** —— `cli_[a-z0-9]{12,}`（app_id）、`oc_/ou_/on_/om_[a-z0-9]{20,}`（chat/open_id、消息号）、飞书文档 token。常混在技能正文和脚本里（配置示例、群映射表），**漏一条 = 泄露自家应用凭据**。
3. **密钥 / 令牌** —— `sk-[A-Za-z0-9]{16,}`、`Bearer <长串>`、平台授权码。技能正文里写着"已配置的示例 key"的**就是真 key，必删**。
4. **真实邮箱 / 手机号** —— 老板或成员的邮箱、内测手机号。
5. **内部路径** —— `<HERMES_HOME>`、`/opt/知识库`、`/root/`、`profiles/<成员名>`、容器路径 `<VOLUME>`、Windows 侧 `AppData/Local/hermes`、`C:/Users/<本机用户名>`。
6. **主机 / 本机名** —— LENOVO、品牌机名、主机名（→ `本机`/`<user>`）。
7. **客户 / 项目名** —— 己方服务过的客户与项目。**这条最容易漏**，泄露的是商业关系。
8. **旧组件 / 产品名** —— 已停用的框架或产品名（如迁走后的旧容器/旧平台）。

**替换铁律：长词优先**。把「主脑X」这种复合词排在「主脑」「X」单字之前，否则短词先替换会把复合词拆碎、留下怪词或残留。每个身份词单独列进词表，**不要用一次「X」→`` 兜底**（会误伤正文）。
只处理文本扩展名：`.md .txt .py .json .jsonl .yaml .yml .sh .csv .js .ts .html .toml .ini .cfg`。

### 替换解决不了的，直接删（关键，别只想着"换词"）
- **技能自带的 `references/` 常是己方内部资料**（战略规划、定价策略、客户案例、调研报告）。这类**整篇删除**，不要逐词替换——替换后正文仍在，等于把商业机密换个称呼发出去。
- **强依赖己方环境的技能整技能剔除**：SKILL.md 的核心指引指向己方专有 CLI / 专有脚本路径 / 内部数据库的，客户装上就是死链，装了也用不了。
- 删文件后**清死链**：SKILL.md 里指向已删文件的引用行一并删掉，否则 AI 会照着去找不存在的文件。

脚本：`scripts/sanitize_skill_pack.py --dir <skills目录> [--dry-run] [--extra-words 词表]` —— 改写 + 复扫 + 体检（frontmatter / 死链 / 图片 / 可用性分级）一次跑完；成员花名/品牌/客户名走 `--extra-words`（每行 `原词\t替换词`）。**至少跑两轮**，第二遍模式放更宽。

### 语义泄漏：换词治不了句意（外发尤其致命）
正则只动字面，**句意照样漏**——扫描报「0 命中」而人一眼看得出来。实测三类残留：
- **术语级**：某套私人体系的行话（偏好维度/玄学/内部方法论术语）→ 换通用表述或整句删。
- **归因级**：「配色铁律（老板钦定，偏好维度土）」字面换掉后，下一行仍写着「依据：老板偏好维度参考……（土第一、金第二）」——等于把主人的私事换个说法发出去。
- **元数据级**：`author:` 里的成员花名、`metadata.hermes.tags` 里残留的替换词、`related_skills` 指向**不在发布集里**的技能（读者/agent 照着找不存在的东西 → 死链）。
做法：**替换之后再逐文件通读一遍**（frontmatter + 命中行上下文），整句/整段改写或删除。**这一步不能交给纯脚本**，也不能只信自己的规则表 → 加一道**独立二审**（见「发布到公开仓库」）。

## 第 4 步：校验（三关都过才算完）
1. **残留扫描**：身份词 + `cli_/oc_/ou_` + 内部路径，必须 **0 命中**。
   **坑**：bash 双引号里 `grep -E "cli_[a-z0-9]\{12,\}"` 的 `\{12,\}` 被当**字面量**（不是量词），会假阴性报 0 命中——看着干净其实没查。→ 用**单引号** `grep -E 'cli_[a-z0-9]{12,}'`（无转义）或直接 Python `re`。
2. **frontmatter 合规**：每个技能目录有 `SKILL.md` 且含 `name` + `description`；`name` 与目录名一致，**用 ASCII**（中文 `name` 能加载但不规范）。
   **坑**：一遍扫不全。**至少两轮**——替换后再扫一遍，且第二遍用**更宽**的模式（容器路径 / 本机名 / 旧产品名 / 客户名 / 密钥 / 真实邮箱）。第一遍通常只清掉最显眼的三四类，剩下的是事故点。
3. **装载实测（"能用"的唯一硬证据）**：对方是 Hermes 时——
   ```
   hermes profile create ztest --no-skills --no-alias
   cp -r <包>/skills/. <HERMES_HOME>
   hermes -p ztest skills list --source local --enabled-only   # 末行应为 "N local — N enabled"
   printf 'ztest\n' | hermes profile delete ztest              # 删除需交互确认，管道喂名字
   ```
   `enabled` 数 == 包内技能数才算过；有 error/skip 就回去查格式。**别用"格式合规"冒充"能用"，装载给数才是实证。**

## 第 5 步：打包 + 交付
- 打 zip（排除输出目录自身）+ 三个说明文件：`README-先读我.md`（安装：拷进技能目录 → 重启网关）+ `技能清单.md`（分域 + 每项一句说明）+ **`安装与配置指引.md`**。
- **《安装与配置指引》是"能用"的关键**（缺了就是扔一堆文件给对方）：
  - 可用性分级：**开箱即用 N 个**（无 `scripts/`）/ **需装 Python 包 M 个**（有 `scripts/`）。
  - 依赖命令：解析各技能 `scripts/*.py` 的 import，去掉 stdlib 和技能自带模块，汇总成一条 `pip install ...`。
  - 需凭据的技能表：哪些技能要 API Key / OAuth / IM 凭据（按各 SKILL.md）。
  - 附上一步的**装载实测数**。
- **图片要目视核验**：包内若有图片，逐张用 `vision_analyze` 看，确认是自制虚构示意图（水印、假数据），不是真实界面截图。
- 有云文档/大附件的走飞书交付（见 `deliverable-first-delivery`）。
- **交付时必提性能权衡**：技能名 + 描述**每一轮都注入上下文**，装太多会让智能体明显变慢——建议**核心先装 ~100 个，其余按需**。给客户配技能最容易忽略这一点。
- **第三方包**（GitHub 开源等）：保留 `LICENSE` 与署名，**单独说明来源**，不与己方技能混作一团；只挑与接收方岗位相关的域，别整包倒给。

## 变体：发布到公开仓库（比交付一个客户更严）
公开仓库**任何人可见、会被索引和爬虫抓走**，发错了删也留痕 → 脱敏标准比交付客户高一档，多三关：
1. **整技能剔除，只收己方原创**：第三方技能（版权不是自己的）与**含密钥 / 体积失控**的技能一律不发（实测一个第三方技能夹着真 `sk-` 密钥、42MB / 1.3 万文件）。发布集里每个技能先问一句「这是我们自己写的吗」。
2. **整条真实路径 = 身份指纹**：本机绝对路径（`<KB_PATH>`、`<KB_PATH>`）整条替换成 `<KB_PATH>` 之类占位，别只换中间一段。
3. **独立二审后才推**：自己扫过不算数——**换一个视角/模型、不给它你的规则表**，让它直接读文件找隐私与密钥，逐条处理干净再推；推完把仓库内容**读回来**抽查一次。
写操作走 `api.github.com`（Contents API / Git Data API）；镜像只做下载，别指望它 push。机制见 `github-access`。

## 坑汇总
- 知识库 技能目录多为壳（无 SKILL.md），真身在本机 `skills/` → 复制前校验 `SKILL.md`。
- 按 frontmatter `name` 去重会漏同名技能 → 按目录名映射。
- 脱敏必须长词优先，复合词不与单字混排。
- IM 凭据 / 内部路径要扫到 0 命中；`grep -E` 量词转义坑 → 单引号或 Python。
- 外部包主站（github.com）不通时，试 `codeload.github.com/<owner>/<repo>/zip/refs/heads/<branch>`。
- 别只给清单不给包：老板要的是"拿去就能装"，清单是附页不是交付物。
- **脱敏一遍不够**：只替换身份词 ≠ 脱敏。真 key、真邮箱、客户名、容器路径常藏在 `references/` 深处，第一遍扫不出来 → 至少两轮、第二遍模式要更宽。
- **老板问"脱敏干净了吗"= 要证据**（扫描结果 + 扫了哪几类 + 残留 0），不是"放心"两个字；追问一次就是上一版没清干净。
- **`references/` 里的内部资料整篇删**，别逐词替换。
- **强依赖己方环境的技能整技能剔**，别让客户装个死链。
- **清客户名**：服务过的客户与项目名最容易漏，泄露的是商业关系。
- **只做字面替换就宣布脱敏完成**：术语、归因句、frontmatter/tags 里的残留扫不出来 → 替换后必须逐文件通读，并加一道独立二审。
- **把第三方技能混进发布集**：版权不是自己的，还常夹带真密钥与失控体积（实测一个 42MB / 1.3 万文件）→ 整技能剔除，宁可少发。
- 交付声明里要写清"包不含哪些内部信息"，让老板一眼看到你查过什么。
