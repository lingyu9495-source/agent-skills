# Context Engineering

## 概述

每个 AI 智能体都有上下文窗口限制。Context Engineering 不是工具文档，而是一套**「在有限空间里塞最有价值信息」**的策略。

**核心问题：** 当前上下文窗口里，每一条信息都应该被审判——它是「必须现在知道」还是「应该在需要时再查」？

## 什么时候用

- 会话变长，感觉推理质量下降（模型开始忽略早期指令）
- 用户给出大量背景信息/文件，需要判断哪些放入上下文、哪些留作参考
- 多步任务进行到一半，发现上下文已占满，模型开始「遗忘」
- 设计 Skill 时：Skill 的内容如何结构才能最大程度节省上下文
- 创建 Cronjob 时：Cronjob prompt 应该有多长，附带的 Skills 是否过多
- Delegate_task 时：子代理的 context 字段应该放多少信息

## 核心原则

### 原则1：信息分层

```
P0 - 必须始终在上下文中
├── 系统指令（System Prompt）
├── 当前活跃任务的目标
├── 用户最新的一条消息
└── 用户的核心身份/偏好

P1 - 应该在上下文中，但可压缩
├── 正在处理的文件内容
├── 上一步的中间结果
├── Skill 的核心步骤
└── 环境配置/API密钥

P2 - 需要时再加载
├── 历史会话记录（session_search）
├── 完整的Skill内容（skill_view）
├── 用户不常用的偏好
├── 旧的文件版本
└── 已完成的子任务日志
```

### 原则2：先查后放

永远不要让「查一下」的信息占据永久上下文：

```
❌ 错：把用户3年前的简历放在上下文开头
"用户张工，35岁，上海人，本科"

✅ 对：把关键信息放在 Memory，需要时自然加载
"用户的完整背景已存储在 Memory，每次对话自动注入关键摘要"
```

### 原则3：Skill > 内联

```
❌ 错：把整个工作流写在 prompt 里（占上下文）
"第一步做X，第二步做Y，第三步做Z..."

✅ 对：加载 Skill，只引用步骤名（省90%空间）
"按 skill_view('something') 的步骤执行"
```

### 原则4：一件事，一个上下文

一个上下文窗口专注一个目标。需要做的事越多，每件事的处理质量越差。

```
❌ 错：同一会话里既写报告又修bug又回答用户问题
✅ 对：写作→子代理(delegate_task)；修bug→子代理；回答问题→当前会话
```

## 上下文预算分配

### 默认分配模型（假设40K上下文窗口）

| 占用项目 | 估算字节 | 占比 | 说明 |
|---------|---------|:----:|------|
| System Prompt + Memory | ~8K | 20% | 用户身份+系统指令+持久记忆 |
| 当前用户消息 | ~4K | 10% | 用户最新的1条或2条 |
| 活跃的Skill内容 | ~6K | 15% | 当前加载的 skill_view 内容 |
| 中间工具结果 | ~8K | 20% | 未压缩的 terminal/read 输出 |
| 最近对话历史 | ~8K | 20% | 最近3-5轮对话 |
| 剩余预算 | ~6K | 15% | 模型推理空间 |

**当任务消耗超过80%上下文时，应主动干预：**
- 用 `delegate_task` 把子任务外包出去（子代理有自己的新鲜上下文）
- 用 `execute_code` 替代多步 tool call（代码内部处理，只返回结果）
- 压缩长输出：用 `grep` 或 `head -20` 截取关键部分

### 预算告急信号

| 信号 | 可能原因 | 应对 |
|------|---------|------|
| 模型重复之前的回答 | 上下文太长，模型失去跟踪 | 开始新会话/用子代理 |
| 模型忽略早期指令 | P0信息被推到窗口外 | 检查上下文顺序，P0放最前 |
| 推理变慢/冗长 | 上下文碎片化 | 压缩历史，删冗余 |
| 工具调用频繁出错 | 上下文污染 | 用 delegate_task 隔离 |

## 四种上下文模式

### 模式A：直线模式（默认）

```
[System] → [Memory] → [Skill] → [History] → [User] → [Response]
```

**适用：** 单一目标的日常对话
**风险：** 历史积累 → 早期指令被推走

### 模式B：分层模式（推荐用于复杂任务）

```
Layer 1: [System + Memory + Active Goal]  ← 固定，不滚动
Layer 2: [Current Step + Related Data]     ← 随步骤更新
Layer 3: [History Summary]                 ← 替代完整历史
```

**适用：** 多步复杂任务
**优势：** 关键信息不被滚动推出

### 模式C：委托模式（用于极复杂任务）

```
Delegate:
  Context = {goal + exact instructions + minimal background}
  → 子代理有新鲜上下文，专心处理一件事
```

**适用：** 任务有多步骤/多维度
**优势：** 每个子代理95%上下文聚焦在单一任务

### 模式D：巡检模式（用于长期任务）

```
每10轮对话：
  → 检查当前上下文状态（占了多少？还剩多少？）
  → 如果 >70% 已占用：
    ✓ 用 execute_code 处理中间数据（不占上下文）
    ✓ 用 delegate_task 外包非核心步骤
    ✓ 压缩/删除已完成的历史轮次
```

**适用：** 超长会话（30+轮）
**优势：** 保持整个会话周期的推理质量

## 技能设计中的上下文优化

### Skill 内容结构优化

| 写法 | 上下文消耗 | 可执行性 |
|------|:---------:|:--------:|
| ❌ 情景化长篇（"想象一下你正在..."） | 高 | 低 |
| ⚠️ 混合型（概述+步骤） | 中 | 中 |
| ✅ 最小化型（步骤+命令+陷阱） | **低** | **高** |

**上下文友好的 Skill 结构：**
```markdown
## 步骤
1. 具体命令：[command]
2. 具体命令：[command]
3. 验证：[verify command]

## 陷阱
- 纠正历史见 `references/history.md`
```

**在P0/P1定义上的优化：** 确保用户的核心偏好/身份出现在 Memory 最前面（System Prompt 后优先注入），不会在长对话中被推到窗口外。

### Skill 自动加载 vs 手动加载

| 方式 | 上下文成本 | 推荐场景 |
|------|:---------:|---------|
| 技能自动注入（system prompt 中的 always load） | 高（每轮都占） | 仅用于最常用的3-5个核心技能 |
| Cronjob 静态绑定 | 中（任务启动时加载） | 定期任务 |
| 按需加载（`skill_view`） | 最低（用时才加载） | 大多数场景—**优先采用** |

## Delegate_task 上下文策略

### context 字段的最佳长度

| 任务类型 | 推荐context长度 | 原因 |
|---------|:--------------:|------|
| 简单工具调用 | 0-500字节 | 子代理只需知道目标 |
| 代码实现 | 500-2000字节 | 需要完整背景+文件路径 |
| 研究/分析 | 1000-3000字节 | 需要方向+约束+输出格式 |
| 复杂多步 | 1500-4000字节 | 需要完整上下文，但不要传整个历史 |

### context 字段的「必须包含」

```python
delegate_task(
    goal="...",  # 一句话目标
    context="""
    ## 任务背景
    [为什么做这个任务]

    ## 已知信息
    [关键数据/文件路径/API文档]

    ## 约束条件
    [输出格式/质量标准/禁止做的事]

    ## 验证标准
    [如何判断成功]
    """,
    toolsets=[...]
)
```

### context 的「绝不该包含」

- 对话历史（子代理不需要知道前面的对话）
- 用户的非相关偏好
- 已完成的其他任务详情
- 与本任务无关的文件内容

## 日志输出压缩策略

工具输出经常占据大量上下文。压缩策略：

| 场景 | 压缩方法 | 上下文节省 |
|------|---------|:---------:|
| 大文件读前几行 | `read_file(path, limit=20)` | 90% |
| 命令行输出太长 | 管道 `| tail -20` | 80% |
| 搜索结果太多 | 加 `limit=5` | 90% |
| 列表大量文件 | `search_files(limit=10)` | 80% |
| 大段中间数据 | 用 `execute_code` 处理，只返回结论 | 95% |
| 日志文件 | 用 `grep -i error` 只取错误行 | 95% |

## 与 Memory 系统的协同

```
Memory 存储的是「稳定、可复用的上下文缩减器」：

┌─────────────────────────────────────┐
│ 用户身份（User Profile）               │ ← 替代每次重新问用户
├─────────────────────────────────────┤
│ 环境事实（Environment Facts）          │ ← 替代每次重新查
├─────────────────────────────────────┤
│ 偏好规则（User Preferences）           │ ← 替代每次猜用户想要什么
├─────────────────────────────────────┤
│ 操作教训（Lessons Learned）            │ ← 替代重复踩坑
└─────────────────────────────────────┘
```

**每一条 Memory，减少 N 次上下文占用。**

## 常见陷阱

1. **把所有信息都塞进 Memory** — Memory 也占上下文（约8K）。只存」能替代重复上下文」的稳定事实
2. **不分层地堆上下文** — P0/P1/P2不分，结果重要的被次要的推出窗口
3. **大段输出不进代码直接扔给模型** — 用 `execute_code` 处理长数据，只返回分析结果
4. **给 delegate_task 传完整历史** — 子代理不需要知道对话历史，传核心数据即可
5. **忽略上下文压缩时机** — 没发现 >70% 占用就继续对话 → 推理质量下降
6. **Skill 写得比执行步骤还长** — Skill 的目的不是记录一切知识，而是提供最小可执行步骤
7. **不维护 Memory 质量** — 过期/重复的 Memory 条目占据空间但不提供价值

## 验证方法

- [ ] 当前会话上下文预算分配是否合理（P0/P1/P2 分层清晰）
- [ ] 所有 `read_file` 调用是否限制了 limit
- [ ] 所有 `delegate_task` 的 context 是否 ≤2000字节
- [ ] Memory 中没有过时或重复的条目
- [ ] Skill 内容是否符合「最小化型」结构（步骤+命令+陷阱）
- [ ] 长会话每隔10轮检查了一次上下文占用情况
