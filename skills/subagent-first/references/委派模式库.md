# 委派模式库

> 6 种可直接套用的委派模式 + 12 条必须避开的反模式。
>
> 说明：文中出现的 fan-out、fork-join、流水线（pipeline）、MapReduce、侦察兵（scout）等名词，均为**业界通行的工程概念**，此处仅作**类比**帮助理解，不代表本技能源自任何特定文献或实现。本技能为自有方法论沉淀。
>
> 本节内容与平台无关：文中"子代理""后台任务"按你平台的对应机制理解（映射见 `SKILL.md` 的「工具名对照表」）。

---

## 一、六种委派模式

### 1. 并行扇出 fan-out（业界通行概念）

**一句话**：一个输入切成 N 份，同时派出 N 个子代理，各自独立产出，最后由主代理合并。

| 项 | 内容 |
|---|---|
| 适用场景 | 分片之间**互不依赖**、加工口径完全一致。多文件处理、多目录批处理、同一任务的多份平行数据 |
| 任务拆法 | 按目录 / 按文件 / 按数据分片切 N 份，N 一般 3–8；再多就先分批 |
| context 传什么 | ① 这片**只碰哪些输入**（边界写死）② 统一的加工口径 ③ 产出**写到哪个独占路径** ④ 空输入时怎么回（明确要求「返回无文件」而非编造） |
| 验收点 | 每份产出都在独占路径上可被真读回；产出条数与分片输入数对得上；分片之间**没有互相覆盖** |
| 失败降级 | 某个分片失败 → 先单独重派该分片一次；再失败 → 主代理自己做这一片，并在汇总里标注「此片由主代理补齐」 |

---

### 2. 流水线 pipeline（业界通行概念）

**一句话**：把一件长活拆成有先后依赖的若干阶段，每个阶段一个子代理，前一段的产出是后一段的输入。

| 项 | 内容 |
|---|---|
| 适用场景 | 阶段之间有**明确依赖**，且每阶段的产出物可以被落盘检查。抓取 → 清洗 → 分析 → 成稿 |
| 任务拆法 | 按阶段切，每阶段产出**必须落成文件**，下一阶段的子代理只读文件、不读上一阶段的内存 |
| context 传什么 | ① 上一阶段产出的**确切路径** ② 本阶段的输入/输出格式契约 ③ 校验规则（字段、条数、格式） |
| 验收点 | 每阶段产出落盘可回读；下游能仅凭上游文件正常开工（不依赖隐含记忆） |
| 失败降级 | 上游产出不合格 → **在源头修**，不要带着坏数据往下跑；下游开工前先做一次格式校验 |

> 提示：流水线是**串行**的，慢是正常的。如果发现阶段之间其实没有依赖，改回扇出。

---

### 3. 侦察兵 scout（业界通行概念）

**一句话**：先派一两个轻量子代理去「探路」，摸清地形后再决定怎么派主力。

| 项 | 内容 |
|---|---|
| 适用场景 | 任务**边界不明**、不知道有几个数据源、不知道体量多大、直接派主力可能白干 |
| 任务拆法 | 侦察阶段只做**只读**动作：列出文件清单、探查数据结构、确认可行性。产出是一份「地形报告」 |
| context 传什么 | ① 明确要求**只读不改** ② 要回答的具体问题（有几个源？多大？什么格式？有什么坑？）③ 不许下结论，只报事实 |
| 验收点 | 地形报告能直接支撑下一步决策：知道要派几个、怎么切、预期耗时 |
| 失败降级 | 侦察不清 → 别硬派主力。缩小范围再探一次；或直接向用户确认方向，比乱派更省 |

> 侦察兵的性价比在于：**用一点点成本，避免派出一队方向错误的子代理。**

---

### 4. 红蓝对抗双跑（业界通行概念，俗称红队/蓝队）

**一句话**：同一份输入，派两个子代理用**不同立场/不同路径**各做一遍，主代理比对差异。

| 项 | 内容 |
|---|---|
| 适用场景 | 结果**容错低**、怕单点出错、结论需要交叉验证。数据核算、关键结论复核、方案风险评估 |
| 任务拆法 | 两路：一路「按最直接的方式做」，一路「专门找前者的漏洞/反例」。两路**必须独立**，不许共享中间结论 |
| context 传什么 | 各自独立的上下文，写清「你不需要知道另一路做了什么」；产出一份对比表（一致点 / 分歧点） |
| 验收点 | 分歧点被**逐条解释**：是数据源不同？还是方法不同？还是有一方错了？解释不清的标为「存疑」 |
| 失败降级 | 两路结论完全一致也**不能免检**——一致可能是同源错误。此时回到侦察兵，换一个独立数据源重验 |

---

### 5. 批量映射 map（业界通行概念，MapReduce 中的 map 阶段类比）

**一句话**：对一长串同类对象逐个施加同一套操作，每个对象一个子代理，产出后统一收敛。

| 项 | 内容 |
|---|---|
| 适用场景 | 对象数量多但每个都很轻。逐条改名/逐条补字段/逐条翻译 |
| 任务拆法 | 别一个对象一个子代理（开销爆炸）。**按批次分组**：比如 50 个对象一批，一批一个子代理 |
| context 传什么 | ① 本批对象的确切清单（写全，别让子代理自己去猜范围）② 统一操作口径 ③ 逐条产出的格式（编号对应，一条不漏） |
| 验收点 | 产出条数 = 输入条数，**逐条可对号**；出现漏条或错位立即返工 |
| 失败降级 | 某批失败 → 缩小批次粒度重试（大批判失败多半是粒度太粗）；仍失败则主代理兜底那一批 |

---

### 6. 长任务后台化（业界通行概念）

**一句话**：真正**要活很久、要跨会话存活**的东西，不交子代理，交定时任务或后台进程；子代理只负责「有始有终」的活。

| 项 | 内容 |
|---|---|
| 适用场景 | 需要常驻、定时触发、跨会话保持状态的任务（定期巡检、持续监听、长期监控） |
| 任务拆法 | 子代理是**短命**的：它跑完就结束。长任务拆成「后台进程负责持续跑」+「子代理负责一次性分析那批产出」两件事 |
| context 传什么 | 交后台进程：触发条件、间隔、产出位置；交子代理：那一批产出在哪、要分析什么 |
| 验收点 | 后台进程确实在跑（有可观测的心跳/日志/产出更新），不是「启动了就算」 |
| 失败降级 | 后台进程静默 → 不假设它在工作，查日志确认；不可用时降级为「主代理提醒用户手动触发」 |

## 二、十二条反模式（照着避）

> 十二条与 `SKILL.md` 的「常见陷阱」一一对应：坑讲现象，这里讲纠正动作。

### 反模式 1｜为派而派

- **长什么样**：一轮工具调用就能做完的小事也派出去；派出去的开销（写工单、等返回、验证）比自己做还大。
- **代价**：整体更慢，主代理还把「自己动手」的能力荒废了。
- **纠正**：先问一句「这事我自己一轮能做完吗？」能——自己做。

### 反模式 2｜上下文饥饿

- **长什么样**：只丢一个目标（「整理一下那些文件」），不给背景：不给路径、不给口径、不给产出位置。子代理只好猜或编。
- **代价**：产出不可用，返工成本远超省下的那点字。
- **纠正**：目标说**要什么**，背景说**用什么料、按什么口径、写到哪、异常怎么回**。四条缺一不可。

### 反模式 3｜自报即事实

- **长什么样**：子代理回一句「已完成」，主代理就转述给你，没人真的去读那个文件。
- **代价**：**虚假完成**——产出根本不存在，或内容对不上；你被误导，还信任了系统。
- **纠正**：产出必须**实测回读**（路径存在、内容非空、关键值抽查）后才算完成；子代理失败就如实说失败，走降级路径，**绝不编造**。

### 反模式 4｜把拍板权丢给子代理

- **长什么样**：把「要不要做、选哪个方案、能不能上线」这类判断也交出去，让子代理自己定。
- **代价**：责任错位，且子代理视野窄、不许跨方案对比，判断必然偏；出事了没人负责。
- **纠正**：子代理**只出方案和理由，不做最终决定**；拍板权始终留在主代理与用户手里。

### 反模式 5｜拿子代理当常驻进程

- **长什么样**：让子代理「持续盯着」「每天跑一次」——子代理的生命周期与一次委派绑定，会话结束它就没了。
- **代价**：任务在某天悄悄停掉，而所有人都以为它还在跑（假监控）。
- **纠正**：跨会话、要活过本次会话的活，交给平台的定时 / 常驻机制（定时任务、计划任务、后台进程）；子代理只领「有始有终」的活。

### 反模式 6｜多个子代理写同一个产出文件

- **长什么样**：两片范围有重叠，或产出路径都写成 `output.md`，两个子代理同时写。
- **代价**：留下的内容看运气，另一片的工作凭空消失；还可能污染下游结论。
- **纠正**：**一个产出文件只归一个子代理**；要合并就让它们各写各的，最后由主代理合并。

### 反模式 7｜工单过大

- **长什么样**：「把所有资料研究一遍然后写个报告」——一件工单里塞了研究、写作、校对三件事。
- **代价**：子代理在长链路上越走越偏，交回一堆没法验的东西，只能整体重来。
- **纠正**：切小并按阶段串起来——研究归研究、写归写、验归验；每段的产出都能单独验收。

### 反模式 8｜把依赖关系当成并行

- **长什么样**：B 需要 A 的产出，却和 A 同时派出去。
- **代价**：B 只能自己猜 A 的结果，前后口径必然打架，合并时互相矛盾。
- **纠正**：派活前先画依赖图；有依赖的一律串行，或把 A、B 合成一个工单交给同一个子代理。

### 反模式 9｜派完在门口干等

- **长什么样**：派完之后主代理阻塞等待，或者反复轮询产物 / 日志 / 进度。
- **代价**：本想让用户随时能找到你，结果用户还是在干等——纪律白执行。
- **纠正**：派完立刻回到对话状态（汇报一句"已派出谁在干什么"），结果由平台送回；等待期间去处理别的事或主动向用户报进展。

### 反模式 10｜失败后编造结果

- **长什么样**：子代理超时 / 抓不到数据，却把「合理推测」写成「已获取的结果」交上来，主代理照转。
- **代价**：最严重的一条——失败是可修的，假数据会顺着流程一路传下去，污染所有下游结论。
- **纠正**：失败就写失败，附卡点与已排除的路径；缺失部分在交付物里**显式标注为缺失**，不留空白假装完整。

### 反模式 11｜让子代理去问用户

- **长什么样**：把「口径未定」「要不要做」「选哪个方案」这类活派出去，指望子代理去征求用户意见。
- **代价**：多数平台上子代理**没有向用户提问的通道**，只能拿回它自己猜的答案，决策权悄悄转移到看不见全局的执行单元手里。
- **纠正**：需要拍板的活留在主代理；先把选项摆给用户。派活前确认子代理有哪些权限（提问、建定时、写长期记忆通常都不具备）。

### 反模式 12｜不算账就派

- **长什么样**：无视每个子代理独立消耗 token / 配额，把一批很轻的活也拆成十几个子代理；或让子代理把过程日志整段回灌主代理。
- **代价**：账单翻倍、主代理上下文被灌爆，最后还是要人工整理。
- **纠正**：派之前算一笔账——自己做的耗时 vs（写工单 + 等返回 + 回读验证）的总耗时；工单里要求「只回报结论 + 产物路径 + 关键证据」，用结构化回报格式把回灌量压到最小。

## 三、怎么选（速查）

| 你的情况 | 用哪个模式 |
|---|---|
| 分片互不依赖、口径一致 | 并行扇出 fan-out |
| 阶段有先后依赖、产出要落盘 | 流水线 pipeline |
| 边界不明、不知道有几个源 | 侦察兵 scout |
| 容错低、结论要交叉验证 | 红蓝对抗双跑 |
| 同类对象很多、每个都轻 | 批量映射 map（按批分组） |
| 要跨会话存活、定时触发 | 长任务后台化（定时任务/后台进程，**不是子代理**） |

**通用铁律（六条）**：

1. 目的是让用户随时能跟主代理对话，主代理不被重活占住。
2. 预计超 2–3 轮工具调用、或多文件、或长研究、或批量处理的活，一律派子代理后台并行做。
3. 主代理只做四件事：拆解 → 派活 → 收口汇总 → 跟用户对话，不亲自下场做重活。
4. 例外（自己做）：一轮能完成的轻活；需要用户交互/拍板的；有不可逆副作用且需即时把关的。
5. 子代理产出必须验证（路径、回读、实测）后才算完成，自报≠事实；汇总标明哪部分由子代理完成；失败要降级，不得编造。
6. 跨会话、需存活的活用定时任务或后台进程，不用子代理。
