# 子代理优先 · 主代理不下场

> **重活全派出去，主代理永远在线。**
>
> 一句话定位：`subagent-first` 是一套「主代理只拆解、派活、收口、对话，子代理在后台并行干重活」的作业纪律——让你的 AI 助手在你最需要它回话的那 3 秒里，永远有空。
>
> **平台无关**：任何支持子代理 / 后台任务的 AI Agent 都适用（Claude Code / Codex / Cursor / WorkBuddy / Hermes / 其他同类平台），差别只在工具名——见 `SKILL.md` 的「工具名对照表」。

---

## 30 秒见效：用前 vs 用后

| | 用前（主代理亲自下场） | 用后（子代理优先） |
|---|---|---|
| 你发一句「把这 40 个文件整理并出摘要」 | 主代理一头扎进长任务，连续占用工具轮次 | 主代理 3 秒内回你一句「已派 4 个子代理并行处理」 |
| 你想追问、改需求、插一句急事 | **等 20 分钟没人应答**，只能干等或打断 | 随时能对话，主代理一直在线 |
| 重活本身 | 串行，一个接一个，慢 | 后台并行，多文件/多方向同时推进 |
| 做完了你怎么知道 | 你得盯着，跑完才有回音 | 跑完**自动汇报**，标明哪部分由哪个子代理完成 |
| 干得对不对 | 主代理自报「已完成」——无从核验 | 每个子代理产出经**实测回读验证**才算完成，自报≠事实 |

核心区别只有一句：**主代理不是更努力地干活，而是不再被重活占住。**

## 60 秒上手

把 N 个单元**放进一次委派调用**（各平台的工具名不同：Hermes 是 `delegate_task` 收一个 `tasks` 数组；Claude Code 用它的 Task / 子代理工具；其他平台按你平台的子代理 / 任务工具映射）。每个元素就是一个子代理，一次调用并行派出。

每个单元至少写清两样：**要什么**（目标）+ **用什么料、按什么口径、产出去哪**（背景）。示意（字段名按你平台替换）：

```text
单元 1
  目标：整理 docs/a/ 下所有 md 文件，输出一份术语统一表
  背景：输入目录 docs/a/。口径以 glossary.md 为准。产出写到 out/a_terms.md。

单元 2
  目标：整理 docs/b/ 下所有 md 文件，输出一份术语统一表
  背景：输入目录 docs/b/。口径以 glossary.md 为准。产出写到 out/b_terms.md。

单元 3
  目标：对 docs/c/ 做同样的术语统一，产出 out/c_terms.md
  背景：输入目录 docs/c/。口径同上。若目录为空，直接返回「无文件」而非编造。
```

三步走：

1. **拆**——把一件事切成互不依赖的 N 份，每份一个子代理，每份写清目标（要什么）+ 背景（用什么料、按什么口径、产出去哪）。
2. **派**——一次调用把所有单元发出去，所有子代理后台并行跑；派完**立刻回到对话**，不要干等或轮询。
3. **收**——主代理汇总时**逐条验证**：回读产出文件、核对路径、抽查关键结论；标明哪部分由子代理完成；失败的走降级路径（自己做或换方案），**不得编造结果**。

✅ 完成判据：你派出的每个子代理，产出的路径都能在主代理侧被真实验证到。

## 它解决什么 / 不解决什么

| ✅ 它解决 | ❌ 它不解决 |
|---|---|
| 主代理被长任务占住、用户等不到回话 | 让模型本身变聪明——委派不提升单点能力上限 |
| 多文件、多方向的活只能串行慢慢来 | 需要用户拍板/交互的决策（该主代理直接找你） |
| 长任务拖到上下文爆掉、早期信息被挤没 | 跨会话、需要长期存活的常驻任务（用定时任务或后台进程） |
| 重活做完后「自报即完成」、无从验收 | 有不可逆副作用、必须即时把关的操作（主代理自己做） |
| 子代理失败后没人负责、结果被糊弄过去 | 把拍板权丢给子代理——判断权始终在主代理和你手里 |

**边界一句话**：能在一轮工具调用内做完的轻活、需要你拍板的活、有不可逆副作用的活——主代理自己做，**不派**。

## 3 个最常用场景

### 场景 1｜多文件批量处理

- **背景**：一次要处理几十上百个文件，逐个做同样的加工（统一术语、补元数据、格式转换、抽取字段）。
- **拆法**：按目录或按文件分片，每片一个子代理，各自独立、互不依赖——天然可并行。
- **关键**：分片边界要在背景里写死（「你只碰 `docs/a/`」），避免两个子代理写同一个产出文件互相覆盖。
- **验收**：每个产出文件都能被真读回，条数与源文件数对得上。

### 场景 2｜长研究 / 尽调

- **背景**：一个主题要查很多方向、比对很多来源，单线程做完又慢又容易把上下文撑爆。
- **拆法**：按**子主题**或**来源**分派——「你负责政策口径」「你负责市场数据」「你负责竞品动态」，各跑各的。
- **关键**：给每个子代理明确的**产出格式**（要引用、要来源、要结论），否则回来的东西没法拼。
- **验收**：每条关键结论都有可回溯的来源；对不上的地方主代理标注「未验证」。

### 场景 3｜并行多方案对比

- **背景**：同一件事想同时看几种做法，比较后再定。
- **拆法**：同一份输入、同一份约束，派 N 个子代理各出一条方案（方案 A / B / C），约束完全一致才可比。
- **关键**：**拍板权留在主代理和你手里**——子代理只出方案和理由，不做最终决定。
- **验收**：N 条方案在**同一套标准**下被摆在一起对比（成本、风险、耗时），而不是各说各话。

## 什么时候不该派

- 一轮工具调用就能搞定的小事——派出去的开销比自己做还大。
- 需要你确认、选择、拍板的步骤——主代理直接找你。
- 删数据、发消息、发布上线这类不可逆操作——主代理自己做，且当着你面做。
- 跨会话、要活很久的任务——用定时任务或后台进程，别用子代理（子代理是短命的）。
